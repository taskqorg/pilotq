# Route-loop qualification in PilotQ TEST

This checklist qualifies [#220](https://github.com/taskqorg/pilotq/issues/220) on pds18 after the PM installs a merged, released build under [§9](../pilotq.md#9-cli-releases-and-service-operations). Workers do not install live. Production cutover remains unauthorized (R19). Local fixtures prove journal and adapter behavior, not Telegram timing or Codex compliance.

Use the protected owner and an explicitly granted test shell user. Prepare three separate Telegram TEST topics named A, B and C, with two explicitly registered test boards. Keep ordinary workers off any automatic-management test host. Record the release version, source SHA, binary checksum, Telegram message links/screenshots, request audit evidence and timestamps for each case. Never record key values.

1. In topic A send `/loop 1m Read current task status on the first test board; report changes only.` Verify a start receipt, `/loop` mode/next time, then a single tick after one minute. In B ask in plain language to start a dynamic loop watching the second test board. Verify `loop_start` binds that board and `loop_next` records a delay from 60 through 3600 seconds, or `loop_stop` records completion. If the model fails to set a delay, verify the disclosed 300-second fallback and record model compliance as unqualified.
2. In C send a normal question while both loops are due. Verify its 👀 receipt within five seconds, no loop text or board observations in C, and no C text in A/B. Hold a bounded authorized run active in A across two intervals. Verify at most one pending A tick, no second simultaneous A run and continued B/C service. Record receipt and claim times separately from model latency.
3. Exercise plain-language stop in B and `/loop stop` in A. Verify `/loop` reports none and no new ticks arrive after the old running tick settles. Try an out-of-range interval, `/loop@BOTNAME 1m PROMPT`, an ordinary chat user without shell, and a second shell-granted author replacing A's loop. Confirm one loop per destination, appropriate refusal and no effect in B/C.
4. Arm fixed A and dynamic B again. Restart the installed TEST service midway through a delay with `/restart`. Verify healthy restart, unchanged authors/prompts/modes/generations, one overdue tick at most and no native-effect replay from an interrupted tick. Repeat across an update drain; inspect the journal for one enqueue and timer advancement per tick and preserved pending work. Record interrupted work as failed/uncertain, never completed without evidence.
5. On the two test boards use real TaskQ management operations to produce an ask, a review carrying options, a failed move, a dependency-blocked move and a confirmed close. Record the operation's fresh-observable time and the synthetic request's enqueue time: each watched route should wake within 15 seconds while TaskQ is reachable. Confirm the event text stays on the matching route, duplicate observations do not wake twice, the timer still works and only one collector per board serves multiple watches. A review without options must not wake. Board disappearance without confirmed closure must not report a close. Repeat one event while draining, then verify it wakes once after resume.
6. Revoke the test author's shell grant while its loop has a queued tick. Verify cancellation before claim, exactly one route-local stop line and no revival after regrant or restart. Repeat with chat revocation. Send `/new` on the route: verify one reset reply with the loop-stop line, cancelled pending ticks, retained task links and stale dynamic tools refused. Do not grant unknown people to run this case.
7. Simulate a bounded TaskQ read outage. Verify an unknown observer audit event, no invented transition or close, independent service in other routes and the loop timer fallback. Restore access and confirm deduplicated recovery. Record any timing gap explicitly.

Cleanup: stop all test loops in their original routes, confirm `/loop` lists none, settle test tasks through TaskQ and revoke temporary grants. Record A2–A7 pass/fail with evidence, unresolved model/platform timing gaps and cleanup. Do not infer qualification from this checklist's existence.
