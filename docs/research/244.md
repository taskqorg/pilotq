# Repository-link registration and onboarding (#244)

## Question

Can the owner add an existing repository by link and have PilotQ finish its local
registration and onboarding work without requiring a fixed request format?

Source: [task #244](https://github.com/taskqorg/pilotq/issues/244), including the
original request, “add project pah - https://gitlab.ufobe.com/gradus/pah, add it to
taskq”, and the approved bounded-attach answer. [Contract §5](../../pilotq.md#5-taskq-tools-and-project-administration)
owns the resulting behavior and authority.

## Findings

- The old `own_word` check required standalone repository and host tokens. With
  that guard restored temporarily, `cargo test --locked
  project_244_repository_link_registration` failed on the first HTTPS link (exit
  101). The same check passed with the URL-pair validation. Invented hosts/repos
  and quoted links still fail before a local root is created (R10, R15).
- Registration now runs onboarding immediately. The request-255 regression admits
  the original text through CLI and Telegram paths, then uses invented board,
  doctor and service boundaries to verify configuration, service registration,
  owner-only claim/key gaps, one Recheck card and readiness after those owner
  prerequisites are supplied (R13, R17). It performs no real repository or board
  registration.
- [TaskQ v4.6.56 host-service details](https://github.com/taskqorg/taskq/blob/v4.6.56/docs/design/host-service.md#contract-detail)
  define the explicit project registry, locks and wake marker. `service install`
  can also upgrade an image or change the host unit, so PilotQ never invokes it.
  Attach uses only that registry protocol on a healthy existing host, with native
  identity, transition, registration and current-authority checks (§§4–5).
- The fixture verifies missing/stale services, pending installation and lifecycle
  operations, busy locks, foreign board/native identity, symlinks, changed roots,
  cancellation, revocation and fencing. These paths leave the registry and unit
  unchanged. Recheck after a recorded publication intent keeps one entry;
  registry mode and existing entries survive. New entries default to focus off.
- Missing project observations no longer become invented capacity/grant remedies.
  PilotQ retries delayed service observations itself. Existing healthy service
  projects retain their read-only onboarding path; the existing CLI/Telegram
  Recheck regression passes without weakening its assertions.
- The compiled manager policy tells both front ends to correct refused tool
  arguments or ask one plain question, never demand fixed wording. The policy
  loading check proves instruction presence, not real-model compliance (R19).

## Options

1. **Bounded registry attach, implemented.** Completes the approved local steps
   without touching the host unit. Cost: the adapter follows TaskQ's installed
   registry/locking protocol and refuses unknown or pending state.
2. **Call `service install`, rejected.** Reuses its full installation flow, but
   could upgrade or change the unit and conflicts with the approved boundary.
3. **Leave all service registration to the owner, rejected.** Adds no adapter,
   but does not satisfy A4 or the owner's bounded-attach answer.

## Verdict

Confirmed for the local regression and invented registration/onboarding chain.
Affected development checks passed: `cargo test --locked project_244`,
`cargo test --locked onboarding_168_cli_telegram_recheck` and the existing
onboarding component cases. After the required rebase, `cargo test --locked`
passed 243 checks, with 11 live/environment-dependent cases ignored;
`cargo run --locked -- selftest` passed. Contract lint passed after correcting
two overlong specification lines, retaining the 300-line cap. The SHA-bound
TaskQ hand-in identifies the candidate. Checks use a temporary Cargo home because
the host cache is read-only.

No live service, real repository, model session or host unit was changed. CI on
the merge result and real post-release chat behavior remain separate evidence.

## Recommendation

Deliver through normal review and merge-queue gates, then have the PM run the
original chat request after release (§9). Use the real GitLab repository's
`master` default branch; this change creates no checkout or branch assumption.
Verify the automatic setup, remaining genuine owner steps, one Recheck card and
final readiness. Do not register `pah` manually or install this branch live.
