# Task result images and owner choices

## Question

How can PilotQ deliver accepted board-only CSGO review images and record the owner’s
variant selection in Telegram without a checkout or a second task/answer mechanism?

[Task #273](https://github.com/taskqorg/pilotq/issues/273) requests actual CSGO review
images and variant choices inside PilotQ CSLP. The owning contract §5 now covers bounded
board-bound artifact retrieval, inline images, current access and existing TaskQ choices
(R4, R5, R8, R10, R13, R16, R17). The task links the original owner requirement.

## Findings

Before the change, `cargo test --locked --bin pilotq result_images_273_entry_point`
failed because the scoped image-delivery capability did not exist. The same check passed
after implementation. The first development invocation also exposed an uninitialized
`specq` submodule; initializing the pinned submodule restored the repository's build input
without changing its gitlink.

TaskQ remains the sole source of task state, trusted attachment references and questions.
The narrow artifact exception downloads bytes from the registered project's GitLab uploads
API, with protected `issue_read` key injection and no redirects. Both upload-ID references
and Markdown upload paths resolve to the registered project's API. A web-route 404 never
proves the accepted result is absent. The mechanism follows the documented
[GitLab upload API](https://docs.gitlab.com/api/project_markdown_uploads/#download-an-uploaded-file-by-id).

The requeue identified that the first candidate downloaded whole mixed ZIPs, contrary
to owner note 6555246955. §5 now permits only direct JPEG/PNG transfer: named archives
are refused before dispatch and opaque IDs require image HEAD metadata before GET.
Unsupported HEAD or MIME metadata produces one source gap; there is no archive fallback.
This boundary does not qualify live GitLab HEAD support, which the PM must check.
Inbox clarification 6555301414 allows PM publication of verified Mac images as direct
private-board attachments with original result/source provenance. Qualification must put
those permitted image references in the current trusted outcome; older outcomes are
never searched as a workaround. Named mixed ZIP references are refused without dispatch;
opaque ZIP upload IDs are refused from metadata without a GET body. Generic archive
support is optional under that clarification and is omitted from this image-only path.
Photo bytes and immutable destinations enter the existing outbox. Private source,
task/revision, variant, download timestamp, byte count and CRC32 receipt metadata join
the individual delivery outcome by outbox ID. CRC32 identifies accidental byte changes;
it is not an authenticity proof. Original TaskQ cards retain revision/operation fences.
Visual option answers carry the stable Telegram actor through the existing answer path.

Before remediation, `cargo test --locked --bin pilotq result_images_273_retrieval_boundaries`
failed with `a new outcome cannot reuse old variants`. After remediation the same check
passes: an attachment-free trusted question blocks older result images. The persistent
HTTP check protects the image-only boundary by serving ZIP metadata and requiring no GET
body request; it also retains authentication, redirect, size and revoked-access coverage.
The existing mixed-ZIP reader and its now-inapplicable extraction checks were removed
under the owner's explicit image-only decision, retaining project confinement and bounds.

The contract lint initially rejected an overlong added line. Reflowing that paragraph
and existing architecture lines preserved every clause within the 300-line/400-character
limits; `scripts/check-contract.sh` then passed.

The next review reproduced a separate closed-result defect: a complete open snapshot
omits closed tasks, so image retrieval stopped before dispatch. The retained
`result_images_273_closed_fetch` check failed before the fix with
`Current task revision unavailable; no images queued` and passed afterward. §5 now
explicitly requires TaskQ issue/inbox readback for closed results. Retrieval takes its
revision from the bound inbox and rereads issue content, state and revision afterward;
a changed or reopened task cannot queue the old batch. The regression uses a board-only
fixture with no open tasks and verifies the image-only gap under the closed revision,
then simulates reopening and verifies no second batch. Existing HTTP and photo transport
checks independently cover byte retrieval and inline delivery.

Inbox note 6555387134 limits grant negatives to owned isolated fixtures. A273 now
requires the live authorized owner selection and repeated tap readback while explicitly
forbidding changes to real grants, capacity, models and unrelated services. Security
negatives not exercised live remain unqualified; fixture checks retain those protections.

## Verification and open qualification

The focused `result_images_273` checks cover protected HTTP dispatch, project-bound upload
references, image-only dispatch and latest-outcome isolation, actual multipart Telegram photo transport, durable
receipts and access/rebinding boundaries. Existing answer tests retain stale, unauthorized,
repeated and same-operation recovery protections. The candidate gate and PR identity are
reported in the task result rather than inferred from implementation.

The [A273 checklist](../acceptance.md#a273--board-only-task-result-images-and-visual-choices)
reserves real images and a disposable choice round trip for the PM after merged release.
No live service installation, real artistic choice, paid provider or production cutover
was performed by the worker (§9, R19).

## Options

- Use board-bound upload bytes and the existing outbox/question boundaries, as implemented.
  Advantage: inline images and exact option/actor receipts work without a checkout.
  Cost: authenticated artifact retrieval and media errors need explicit qualification.
- Keep link/ZIP-only reports. Advantage: no additional media handling. Disadvantage:
  this fails the owner's inline-image requirement and is not an accepted alternative.

## Verdict

The closed-fetch check failed before and passed after this remediation; all six focused
`result_images_273` checks passed with `CARGO_HOME=/tmp/pilotq-273-cargo`.
The default Cargo cache was sandbox-blocked (read-only Git store); it is not a pass.
The final rebased candidate gate is recorded in the task result.
Real CSLP images, GitLab image metadata availability and the disposable answer round trip
remain PM qualification after merged release. [PR #289](https://github.com/taskqorg/pilotq/pull/289)
requires green merge-result CI. No live installation or cutover is claimed.

## Recommendation

Merge through the qualified merge queue, then release and execute the existing A273 PM checklist.

Keep the scoped upload/outbox implementation and the original TaskQ answer protocol.
Record the PM's real-image and disposable-choice evidence before claiming live qualification.
