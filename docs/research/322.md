# GitLab 17.2 image retrieval (#322)

Repair for [task #322](https://github.com/taskqorg/pilotq/issues/322), under
pilotq.md §5, R13 and R16. Version 0.2.39 remains unchanged. No live installation,
credentials, grants, service settings or private assets are changed by this work.

## Question

Can producer-bound upload IDs restore image retrieval on GitLab 17.2 while keeping
project identity, authentication, image-only transfers and durable delivery fences?

## Findings

### Failure and protocol evidence

The supplied private PM probe record retains the exact failing requests and HTTP 404:
GitLab 17.2.9 returns 404 for authenticated secret/filename HEAD and GET, using both
encoded namespace and numeric project paths. Project identity and upload listings
return 200 with the existing authorized issue-read key. The producer separately
reported the same GET failure. These are supplied live observations, not new worker
network probes. No private URLs, routes, hashes or asset bytes are published here.

The [GitLab upload API](https://docs.gitlab.com/api/project_markdown_uploads/)
introduced by-ID downloads in 17.2 and secret/filename downloads in 17.4; upload POST
responses gained an ID in 17.3. The older server therefore cannot supply the current
secret/filename API route. Web redirects are not a permitted fallback.

The producer subsequently verified the two upload IDs and published a new trusted
ask, superseding the old ask. Its verification explains the 118-byte increase as
server JPEG metadata rewriting, with equal decoded RGB pixels and orientation.
Those producer findings are retained privately; this worker does not infer upload
identity from matching filenames, sizes or HTTP 200.

## Change and retained protection

Numeric project identity is preserved instead of silently replacing it with the
registered namespace. Before reading an upload, authenticated project metadata must
match both the numeric ID and registered namespace. The read is bounded to 256 KiB,
uses the existing scoped issue-read key, checks current access and follows no
redirects. The existing exact-ID image metadata lookup then gates octet-stream
transfer. Producer-bound `#upload=<id>` references select the exact positive ID;
unknown fragments, non-image paths and foreign origins remain refused. A path-only
404 stays a gap; no upload discovery, archive or arbitrary web fallback is added.

Latest trusted outcome selection, task revision readback, route/actor fencing,
image signatures, MIME and size checks, original captions, duplicate guards and
individual Telegram receipts retain their existing boundaries. The trusted labels
carry ct01-usp/#444 and t02-akm/#444 provenance through download and queueing.

## Verification

The new reference regression failed before the fix because the numeric project
was replaced with the encoded namespace. The HTTP protocol regression also failed
with the old mapper: its first request went to the namespace upload listing rather
than numeric project identity, and zero of two images were returned. Restoring the
fix passes both regressions.

The filtered image suite covers two by-ID JPEG responses with octet-stream metadata,
preserved provenance labels, foreign namespace and mismatched project ID, 401/403,
redirects, unsupported sources, 404, MIME/signature/size failures, revoked access,
stale revisions, route/actor/repeat guards and actual multipart Telegram photo
transport. Fixtures contain invented keys and project identities only. Existing
exact-ID metadata checks retain encoded namespace fixtures; new checks independently
exercise numeric project validation. No decided assertion is weakened.

Initial test setup was blocked by the read-only default Cargo cache and missing
specq submodule. A temporary Cargo cache and initialization of the pinned submodule
resolved those setup issues; neither initial failure is product red/green evidence.
Candidate gate and independent review results are recorded in the TaskQ result/PR.

## Open qualification

Local protocol and transport checks do not establish actual live Telegram delivery.
The retained 0.2.38 failure remains unclaimed. Publication requires independent review
and green merge-result CI. Before release the PM alone runs combined final-source
all14 and independent cleanup, verifies the installed binary, requests images again
through the normal authorized route, checks both inline photos and provenance
captions, and only then answers the TEST card (§9, R19). Old observed markers and
SQLite are not edited to force redelivery.

## Options

- Use producer-bound IDs with authenticated project verification (implemented).
  Benefit: uses the supported 17.2 API and retains image identity. Cost: the producer
  must verify and publish IDs; old path-only outcomes remain unavailable.
- Retry secret/filename or web routes. Benefit: needs no new trusted references.
  Cost: unsupported on 17.2 or requires forbidden redirects; rejected under §5.

## Verdict

Local protocol and image checks pass with the fix, and independent review found no
blocking defects. The supplied live 404 evidence establishes the old failure; live
correction and merge-result CI remain unqualified.

## Recommendation

Require green merge-result CI, then complete the PM-only qualification above before
release and before answering the TEST card. Keep version 0.2.39.
