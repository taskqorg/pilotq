# Board lists with a remembered project (#250)

An unnamed board-list request in a Telegram topic without a route binding must return every
accessible board, even when the conversation remembers a project (§5, R13, R17).
The [task](https://github.com/taskqorg/pilotq/issues/250) retains the original request and acceptance;
answer 6547309963 supplies the read-only live evidence and authorizes this interpretation.

## Root cause and evidence (A1)

The PM observed PilotQ 0.2.34 at source `76e2f3af` on pds18. Request 259 contained
`сделай таскью-лист`; its `project_status` call had arguments `{}` and returned:

```text
Which project: cyprusbz, pilotq, tight? Nothing was done.
```

The shared topic had no `route_projects` entry. Its conversation, however, retained
`project='pilotq'`, selected earlier by the owner. The #243 aggregate branch checked
`current_project`, which combines remembered selection and route binding. That selection skipped
the aggregate branch. Single-project resolution then called `context_project` before using the
current project; ambiguous earlier own references produced the error. The aggregate branch was
already before that resolver: the original suspected ordering was not the cause.

A completely unselected topic with an older open project question passed unchanged. Adding the
remembered project reproduced the exact refusal. The supplied live evidence establishes the
remembered selection; an open project question is an additional acceptance-case condition, not a
claim about request 259's live cards. The PM reported no open question on its recent plan cards.

## Change and regression evidence (A2)

The aggregate branch now distinguishes an explicit topic route binding from a remembered
conversation selection. It reads all accessible boards for an unnamed list in an unbound topic,
without clearing that selection. Current own project references, bound topics and CLI/DM current
selection retain their scope. Each board still uses the installed TaskQ CLI and its own audited
read; partial failure and current grants remain enforced (§5).

The existing `unbound_242_board_list` component check now includes a Telegram topic, remembered
`pilotq`, the same person's older numbered project question and the Russian request with `{}`.
Before the implementation change, `CARGO_HOME=/tmp/pilotq-250-cargo cargo test --locked unbound_242`
failed with the exact refusal above. After the change, the same filter passed: three boards,
one read and audit per board, no new project question, and the remembered selection preserved.
The fixture also retains guessed-argument, unavailable-board and revocation protections, and
checks explicit own project selection and a genuinely route-bound topic. The existing
`project_status` filter passed, retaining single-board snapshot integrity checks. No guarding
assertion was weakened; the original unset-selection assertion still checks the original CLI run.

Candidate gates and exact commit identity are recorded in the TaskQ result and PR. Local checks
qualify the component boundary, not live Codex presentation or Telegram delivery (R19).
