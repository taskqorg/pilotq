# Plan requests ending without an answer (#218)

## Question

Why do plan requests on pilot 0.2.28 finish with “Codex ended the turn without an answer” after successful tools, and how can they return the saved plan card while retaining empty-turn failure cleanup?

Source: [task #218](https://github.com/taskqorg/pilotq/issues/218), including the owner's request “составь план для pilotq: добавить в README раздел FAQ” and PM evidence note 6542216300. This repairs R5/R13 and §12 under the existing §2 plan flow; it does not change success or launch authority.

## Findings

### Root cause from audit and Codex events (A1)

The PM supplied sanitized audits for requests 211 and 215 and their Codex rollout events in untracked `pm-traces/`. These inputs are deliberately excluded from the commit. Both audits show `failed`, the exact empty-answer diagnostic, two completed dynamic tool calls and `revisions: []`.

The events explain why the final audit has no revision:

| Request | Successful `task_plan` receipt | Empty final answer | Terminal observation |
|---|---|---|---|
| 211 | 10:15:28.221Z, 2026-10-31 | 10:15:29.311Z | `task_complete` at 10:15:29.364Z, `last_agent_message: null` |
| 215 | 10:18:11.175Z, 2026-10-31 | 10:18:13.960Z | `task_complete` at 10:18:14.023Z, `last_agent_message: null` |

Both successful receipts include “Draft updated locally; nothing is filed” and “The final reply shows this updated draft with a launch button.” Each final `response_item` has `phase: final_answer` and an `output_text` with `text: ""`. Request 211 also has an earlier commentary message; progress did not establish a useful terminal answer.

Code confirms the chain. `taskq::dispatch_until` saves the draft before returning its receipt. `taskq::INSTRUCTIONS` tells the model not to repeat the saved draft because the renderer shows it, but supplied no requirement to send a nonempty acknowledgement. `Codex::turn` rejects a completed turn whose last agent message is empty. `Journal::finish_with_footer` then calls `discard_failed_drafts`, preserving its tickets as a `failed_draft` audit event and removing the unlaunched revision. Thus the empty audit revision list does not mean that `task_plan` failed.

The root cause is the mismatch between plan-specific suppression of final prose and the adapter's required nonempty terminal answer. Successful plan saving followed by an empty model final was treated as a failed request, so the draft could never reach the card renderer. This is not a project-status, tool-dispatch or Telegram-delivery failure. The model's internal reason for choosing empty text is not observable; the event sequence and local before/after reproduction establish the interaction.

### Repair and before/after evidence (A2/A3)

Clarified the manager feedback detail, TaskQ instructions and successful `task_plan` receipt: send one short nonempty acknowledgement in the person's language. PilotQ replaces it with the saved plan card, rather than delivering a duplicate recap. The existing instruction fingerprint rebuilds conversations when these instructions change. No adapter success condition, draft cleanup, grant, fence or launch check changes.

Development checks use a writable OS-temporary copy of Cargo's cache with `CARGO_HOME`; the default cache was read-only. The worktree's pinned `specq` submodule was initialized before building; its revision is unchanged.

- `cargo test --locked plan_218 -- --nocapture`: before repair, the new instruction-input check failed on the missing nonempty-answer requirement. After repair, both deterministic checks passed; the subscription check is explicitly ignored in the default suite.
- `PILOTQ_A8_CODEX_HOME=<existing subscription home> cargo test --locked --test telegram plan_218_live_model -- --ignored --nocapture`: before repair, the exact FAQ request failed with the empty-answer diagnostic. Its isolated journal recorded successful `project_status` and `task_plan` calls followed by `failed_draft`. After repair, the same request passed in 12.33 seconds with one saved plan and no board writes. This used the existing subscription login, not a paid API (R9).
- The actual after reply was: `**Add a FAQ section to README**`, then `Сделаем: Help README readers find answers to common PilotQ questions.`, then `Готово, когда: В README добавлен FAQ с проверенными ответами на основные вопросы о PilotQ.` This establishes plan completion, not full model-language fidelity.
- `plan_218_empty_turn_and_acknowledgement` runs the shared CLI request/tool/finalization path with the same two calls and either an empty final or a short acknowledgement. Empty still fails in one line, drops the draft, retains its audit evidence and files nothing. Nonempty renders the saved card once and files nothing. Existing #212 bilingual failure, prior-draft preservation and restart tests remain unchanged.

An initial assertion in the new CLI fixture incorrectly expected Russian fixed labels based on its tool JSON, although the own input was English. It was corrected to assert the CLI's English card labels; no product behavior or existing guard changed.

The frozen candidate runs `scripts/check-contract.sh`, `cargo test --locked` and `cargo run --locked -- selftest`; the task result records their observed outcomes and candidate SHA. Local model and fake Bot API observations do not qualify the installed service or real Telegram appearance (R19, §9).

## Options

- Require a short acknowledgement after saving a plan (implemented). Plus: repairs the demonstrated instruction mismatch and preserves all empty-turn protections. Minus: model adherence still needs qualification; future genuinely empty turns continue to fail explicitly.
- Treat any successful `task_plan` as success despite an empty final. Plus: avoids relying on an acknowledgement. Minus: changes A3's empty-turn/draft-cleanup protection and could publish drafts from failed turns; not adopted.
- Retry the model turn automatically. Plus: might obtain prose on a later attempt. Minus: repeats work and risks effects; unnecessary and inconsistent with §5's no-replay boundary.

## Verdict

The observed failure is reproduced and repaired locally, including an actual subscription-model before/after check. Empty-turn failure and failed-draft cleanup remain protected. No deployment or full task completion is claimed: A4 remains open.
