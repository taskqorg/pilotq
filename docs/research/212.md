## PM post-release qualification

Workers do not install live (§9). After a merged release reaches the test pilot on PDS 18, record the source SHA, version, binary identity, topic and actual replies/screenshots for these seven scenarios in the PilotQ TEST topic:

1. `/help`: short grouped controls, three separate examples, no ordinary-user operator or unavailable commands.
2. Ask task status, including a held task awaiting PM review: essence first, no more than three short bullets, verified short task labels and one localized next-actor line when waiting; no unrelated DEV health.
3. Request a multi-task plan: localized summaries, blank lines between tasks and the existing Launch/Cancel buttons. Exercise a failed plan request separately: one plain localized failure line, no shell output and no saved draft.
4. `/status` after a model failure: plain reason, person's language and next actor; no diagnostics.
5. Ask which projects are available: retain the compact available/current-project result.
6. Follow up with “and tight?”: retain target resolution, follow the original question's release/health scope, and keep the short reply shape.
7. Save a draft and press Cancel: edit its source card in the person's language, remove buttons, create no task and make no model call.

Repeat in Russian and English. Also ask an explicit release/health question to prove its useful observations remain available. Record the failure test's audit/draft readback without publishing command bodies or private paths. Green local tests or CI do not substitute for these model and target-platform observations.
