# TaskQ-only board access: task #144

## Question

Can PilotQ use `https://gitlab.ufobe.com/gradus/tight` for infrastructure work on PDS 18 without implementing a second board adapter?

## Findings and evidence

- Before the change, PilotQ constructed `https://github.com/{board}/issues/{task}`, parsed GitHub issue paths and read board answers through gh. A GitLab project registration alone could not qualify that path. The original #144 attempt observed unauthenticated project/board HTTP 404/401 while the network was reachable; this did not prove authenticated permissions.
- The owner selected TaskQ-only board access in [#144](https://github.com/taskqorg/pilotq/issues/144), notes 6509520977 and 6513810878. The root contract §5/§9 records this decision before implementation (R13).
- TaskQ 4.6.43 `inbox 144 --json` returned schema 1 and accepted answers with `by`, `at`, `revision`, `text` and `late`. `status --task 144 --json` returned a complete board snapshot and canonical task URLs. This proves the installed CLI interface, not the Telegram flow or GitLab access.
- PM note 6511752122 reports `tight` registered alongside `agentq` and `pilotq`, with a complete `gradus/tight` snapshot containing zero tasks. This is PM-supplied target evidence. The installation's `current` entry is a non-executable version marker selecting 0.2.14. Running that release's `projects list --json` was sandbox-blocked: `attempt to write a readonly database`. This is not a passing project-list check.
- TaskQ's published command contract has no direct arbitrary-issue read, comment, label or legacy effect-readback commands. These tools therefore refuse explicitly; old unresolved effects remain uncertain and are never replayed. The attempt to file a TaskQ finding was rejected because the finding board must match the configured board. No finding was created; PM must file it on taskqorg/taskq with its authorized configuration.

## Options

1. Reuse TaskQ CLI (selected). Pro: forge credentials and trust stay in one place. Con: missing direct-issue features require upstream work.
2. Add a PilotQ GitLab adapter (rejected). Pro: a separate integration could expose additional forge data. Con: it duplicates authentication, trust and effect recovery.

## Recommendation

Implement the owner-selected CLI path only, preserving grants, operation receipts and original destinations. No new product decision is requested.

## Verification and remaining work

The focused regressions cover GitLab-shaped TaskQ status and URLs, unchanged project visibility, empty versus unreadable snapshots, canonical answer/question binding, stale callbacks and restart receipts. They are adapter/process checks, not live GitLab or Telegram acceptance. An isolated `matches_taskq_readback` regression compiled the link helper from base `d24207aa703c19f08cac586ddabb90e678e55add`: it failed with a synthesized GitHub URL for the invented `gradus/tight` fixture. The same readback assertion passed using the changed helper and the supplied GitLab URL. This is helper-level before/after evidence; `gitlab_registry_status_and_urls` additionally passed the CLI-to-tool path. Exact candidate gate outcomes belong to the task result and PR.

PM owns release and the A3 authorized Telegram readback after merge. Record source links and revisions under the root contract §5. A board can hold infrastructure tasks, but registration alone grants no access to PDS 18: execution needs TaskQ setup, an authorized worker/runtime, resource grants and board qualification (A4). No installation change or server-access grant is made by this PR.
