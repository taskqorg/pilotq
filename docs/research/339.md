# Native rebuild audit reasons (#339)

PilotQ now records the known rebuild trigger at the shared journal boundary: planned policy
refresh, foreign runtime, or native session unavailable after failed resume. This implements
[task #339](https://github.com/taskqorg/pilotq/issues/339) under R17 and
[runtime §3](../runtime-contract.md#3-architecture-and-ownership); §4 no-replay protection remains intact.

## Question

How can rebuild auditing distinguish an intentional policy refresh from native-session recovery
without changing recovery behavior or inferring historical causes?

## Findings

Before editing, the worker read the accepted #337 diagnosis and its ignored private proof.
The accepted diagnosis found the original rollouts intact, with thread/start and no
thread/resume in the request 395/402 start windows. Changed hashed instructions strongly
support policy refresh; historical refresh flags and fingerprint values were not recorded,
so the exact historical trigger remains unknown. The old audit label alone proves neither
missing persistence nor a failed resume. The proof's early request-402 running-state caveat
is superseded only by the accepted terminal observation: 315.001477 seconds, exit 0.
No historical audit, native store or live journal was modified or repaired.

`cargo test --locked --bin pilotq instruction_change_rebuilds_once` failed before the fix:
expected `planned policy refresh; journal context prepared`, observed
`native session unavailable; journal context prepared`. It passed after the fix.
The existing transcript assertions remain, including reuse of the replacement ID.

`native_rebuild_339_reasons` exercises real CLI/manager/journal wiring with a fake Codex:
unchanged policy resumes th-1 without a rebuild, changed policy starts th-2 with a planned
refresh audit targeting th-1, missing-rollout resume failure starts th-3 with a distinct
recovery audit, and foreign-runtime state starts another thread without attempting resume.
The test reads the actual app-server calls and persisted IDs/reasons. It uses only disposable
fixture state and does not qualify live subscription behavior.

The existing `c06_resume_failure_rebuilds_without_replaying_effects` check additionally
retains task receipts, recovered history, exactly one external effect and replacement-session
continuity, and now requires the failed-resume audit reason. Recovery context, fencing,
replacement finalization, AgentQ pin and runtime behavior remain unchanged.
