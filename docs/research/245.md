# Member reports and blocker routing

[Task #245](https://github.com/taskqorg/pilotq/issues/245) requires full report access and PM/owner escalation without sending members operator work. The implementation applies §5, R10, R13 and R17; §9 and R19 retain the local/CI versus live qualification boundary.

## Question

Can a project-granted member retrieve a complete task report and its open dependent work, while PilotQ itself routes PM/owner blockers and preserves a plain refusal?

## Findings

- A1: `project_file_read` uses the registered checkout's default-branch reference and returns its pinned commit. It reads regular Git blobs, never working-copy files. Current chat/project grants, run fencing and registration revalidation protect disclosure. The ten-second reader caps text at 256 KiB and rejects traversal, symlinks, directories, binary and oversized content. Missing refs or objects are unavailable. Remote freshness is explicitly unknown; no fetch or working-tree mutation occurs.
- A2: `issue_read` retains the complete trusted closing comment, including one older than the latest ten comments. A fresh complete matching TaskQ snapshot supplies open reverse dependencies through typed `deps`; prose mentions never establish dependency. `task_status` includes the same reverse lookup. Existing ordinary-comment and body excerpt protections remain.
- A3: `member_blocker` queues one durable owner DM notice per request/project. The protected owner is the PM fallback. The notice contains member, request and project identity; the member receives factual queued/unconfirmed wording. Grant checks, audit and transactional outbox persistence retain authority. Repeated calls reuse the notice. Manager instructions prohibit assigning members PM or owner work.
- A4: plan cards, immediate launch refusals, recovered submission receipts and failed-turn replies retain the localized setup refusal and notification outcome. Owner remedies remain in the owner notice; member text does not offer Recheck or owner commands. A failed notification is reported as unconfirmed, never delivered.
- A5: `member_245_file_and_blocker` protects grant/cap/path boundaries, immutable source selection, English/Russian refusals, owner routing, deduplication, restart persistence, failed-turn fallback and actual launch-refusal dispatch. `member_245_full_report_and_dependents` protects complete closing reports, old reports, reverse dependency lookup and unknown incomplete snapshots. The existing `issue_tools_through_taskq_issue` check also verifies dependents through the actual dynamic-tool boundary and retains GitHub/GitLab reads, owner-only writes and same-operation reconciliation.

## Before and after

The original reader cut every comment at 500 characters. Restoring that cutoff and running `cargo test --locked --bin pilotq member_245_full_report_and_dependents` failed the full-body assertion. With the fix, the `member_245` filter passed both regression checks. The existing `onboarding_236` filter passed three checks; the `issue_tools_through_taskq_issue` filter passed its adapter check. The unchanged ordinary-excerpt assertion still passes. The first full candidate gate exposed an owner no-create-claim reply regression (`f07_board_unavailable_or_no_create_claim` timed out waiting for the established refusal). The code now preserves that owner path; the guarding assertion remains unchanged.

A later full run exposed an existing duplicate-start race: `f02_duplicate_lock_and_conflict` received `database is locked` instead of the poll-lock refusal. Startup now acquires the OS lock after opening storage and before bootstrap or reconciliation, so a contender cannot recover an active service. The existing lock assertion remains unchanged (§4).

The initial Cargo invocation was sandbox-blocked by a read-only dependency cache. A writable temporary cache and the pinned submodule allowed local checks to run. Final candidate gates and publication evidence belong to the SHA-bound TaskQ result.

## Limits

No live installation or Telegram/model qualification was performed. The actual cyprusbz #547/#548 flow remains a PM post-release check under §9; fixtures demonstrate the report/dependency boundaries. Default-branch reads expose the registered checkout's pinned reference, with remote freshness unknown. A missing or stale checkout cannot establish the latest remote report.

## Options

1. Extend typed reads and reuse the durable owner outbox (implemented). Plus: preserves project grants and recovery receipts. Minus: the file source is the registered default-branch ref, with remote freshness unknown.
2. Hand off reports and operator remedies to the member (rejected by A3–A4). Plus: requires no new tool boundary. Minus: reproduces the reported defect and leaves the requested work unfinished.

## Verdict

Confirmed for the local adapter boundary: A1–A5 have regression evidence, including the original truncation failure and the fixed behavior. The final suite passed 242 tests with 11 intentionally ignored; the contract gate and offline selftest passed. Merge-result CI and §9 live qualification remain pending.

## Recommendation

Review and merge only after green merge-result CI, then perform the PM's §9 post-release member/report checks. Retain the explicit unknown remote-freshness limitation.
