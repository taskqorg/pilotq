# Project alias tool lookup (#275)

The defect was a mismatch between own-message alias recognition and exact tool-argument registry lookup. PilotQ §5 already requires `cs` and `cyprusbz` to select the same authorized registered target; this change implements that decision without changing the contract.

## Question

Why does `project: cs` fail after the caller has already named the canonical authorized project through its alias?

## Findings

Before the fix, `cargo test --locked alias_ -- --nocapture` failed both `direct::context_tests::alias_tool_275` and `taskq::tests::alias_status_275` with `cs is not a registered project; nothing was done`. This safely reproduces the lookup defect in A2/A6, not the live request transcript in A1.

After the fix, `cargo test --locked alias_` passed both tests (2 passed, 0 failed) on the rebased candidate. Tests used a writable temporary Cargo cache because the default cache is read-only in the worker sandbox.

The retained regression checks cover the distinct risks in §5 and R4/R10:

- `alias_tool_275`: canonical and alias arguments select the same registered board; direct selection and project switching work. Reads leave the current project unchanged. Verified URLs retain identity checks; conflicting and unverified URLs refuse. Quoted aliases in a fresh generation, revoked grants and absent registration refuse.
- `alias_status_275`: `project_status` and `task_status` accept both spellings through the existing TaskQ executable boundary. A DEV request reaches release observation and reports `Release configuration missing` rather than an alias error. The fixture uses invented board and issue data; it does not prove live deployment ancestry.

A single normalizer reads `PROJECT_ALIASES`. Direct selection, project switching, TaskQ subscription filtering, saved-plan identity comparison and fresh URL filtering use that normalizer before comparing canonical names. No registration, grants or release adapter behavior changes. Saved plans still cannot change to another project; URL identity and registration readback still gate dispatch.

## Remaining qualification

A1's live request 359 on 0.2.37 (three `task_status` failures, `project_use` failure and final unknown DEV ancestry) was supplied as task context, but its live journal/transcript is unavailable within this worker's project-only scope. It was not independently reproduced.

Per §9 and R19, the PM must repeat “Is cs #541 on DEV?” on the ordinary released PDS build, compare the canonical spelling, and retain the request/tool evidence, canonical board, release evidence or exact unavailable reason. Workers do not install live. A successful local fixture is not that PM qualification. GitHub acceptance also requires green merge-result CI (`merge_group`).

## Options

- Normalize through the existing table: preserves one alias authority and existing authorization boundaries; requires updating the affected identity comparisons.
- Require canonical model arguments only: no implementation change; retains the observed failure and violates §5, so it is not an acceptable fix.

## Verdict

Confirmed: tool arguments bypassed alias normalization. The focused checks fail before the fix and pass afterward. Live qualification remains open as described above.

## Recommendation

Accept the code after green merge-result CI, then have the PM retain released-build evidence under §9. Do not infer deployment ancestry from local checks.
