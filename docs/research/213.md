# Scheduled update starvation (#213)

The fix retires terminal request slots and expires inactive slots without imposing a total turn limit. It applies R5, R13 and pilotq.md §§4, 7 and 9. Task #213 note 6541414425 approves inactivity expiry in place of A3’s fixed deadline.

## Question

Why does an idle pds18 service retain a running-request drain slot, and how can it retire the slot without interrupting active work? Acceptance and the approved inactivity decision are in [task #213](https://github.com/taskqorg/pilotq/issues/213).

## Findings

Observed on pds18 through `journalctl --user -u pilotq` on 2026-10-31:

```text
Oct 31 06:20:21 pds18.ufobe.com pilotq[3062819]: pilotq 0.2.24 service running
Oct 31 06:48:06 pds18.ufobe.com pilotq[3062819]: scheduled update: drain: 1 running request(s); update deferred
Oct 31 08:40:32 pds18.ufobe.com pilotq[3062819]: scheduled update: drain: 1 running request(s); update deferred
```

[`src/main.rs::drain`](../../src/main.rs) counted every `requests.state='running'` row. In [`src/journal.rs::finish_with_footer`](../../src/journal.rs), the fenced branch retired only the run, leaving its request running. `Journal::reconcile` selected only running runs, so restart could not repair this terminal-run orphan. Overlapping CLI claims can advance the conversation fence and enter this path. An early `?` error in [`src/manager.rs::run`](../../src/manager.rs) could also escape without finalizing its claimed request.

The local regression demonstrates the terminal-run leak. The old pds18 logs contain only a count, so they cannot identify the original request or distinguish which error/fence transition created its slot. New diagnostics include request identity, conversation, age and idle time for that attribution.

## Protection and evidence

Before the fix, `cargo test --locked drain_213_terminal_slots -- --nocapture` failed:

```text
assertion `left == right` failed: terminal outcome leaked a drain slot
  left: 1
 right: 0
```

After the fix, the same test passes. Its retained cases protect error, timeout, uncertain-tool, fenced and overlapping-CLI outcomes, plus restart recovery and rejection of late replies. `drain_213_manager_error_releases_slot` exercises an actual early adapter error and preserves uncertainty after a tool starts.

`drain_213_activity_and_orphan_recovery` checks the exact 600-second inactivity boundary, recent activity on an older request, stored findings, suppression of unconfirmed effect dispatch, restart repair of a legacy terminal-run orphan, and answer writes without a model run. Runtime messages update one durable timestamp per run; typing and progress do not update it. No schema change is needed.

`cargo test --locked drain -- --nocapture` passed all five selected checks. The existing active-work drain check keeps its assertions; its fixture now uses current time so it represents active rather than expired work. `cargo test --locked runs_reconcile_and_fence` and `cargo test --locked native_and_long_turn_190` passed, retaining cancellation, recovery and active-runtime protection.

`cargo test --locked installed_service_updates_on_schedule` passed. Its installed-service fixture now seeds the old terminal-run orphan, verifies automatic activation exits 75, checks the selected binary, and reads back zero running requests with the orphan marked failed. This is a local process check, not pds18 deployment evidence.

The initial default Cargo run was sandbox-blocked by its read-only cache. Subsequent checks used a temporary Cargo cache. Initial build setup also required initializing the repository’s pinned specq submodule; its pin was unchanged.

The canonical candidate gate passed after the single rebase: `scripts/check-contract.sh`, `cargo test --locked` (211 passed, ten intentionally ignored), and `cargo run --locked -- selftest`. The later report-format correction changes documentation only; executable source and checks are unchanged.

## Options

- Retire terminal slots and expire after ten minutes without runtime events. Pro: preserves active work and follows the approved §7 decision. Con: requires a durable runtime timestamp. Implemented and locally verified.
- Expire by total request age. Pro: simpler age calculation. Con: interrupts active work and conflicts with §7. Rejected in the task’s approved answer.

## Verdict

Confirmed locally: fenced completion leaks a running request before the fix, and the repaired lifecycle permits the installed-service fixture to update automatically. Live pds18 rollout remains unqualified until A4 is observed.

## Recommendation

Accept the locally verified fix through merge-result CI; have the PM qualify the released pilot under §9.

## Remaining qualification
