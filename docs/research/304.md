# A40 native-scope teardown (#304)

R5 and R12 require completing fixture-owned writers before removal; §9 and R19 keep focused checks separate from release qualification.

## Question

Can native-scope teardown establish writer termination before directory removal without changing production lifecycle?

## Findings

### Failure and diagnosis

Task #304 retains the original main CI `41296111065` failure on `30f98bd`: `automatic::a40_native_manager_scope` failed with `DirectoryNotEmpty` at `automatic.rs:892`, after `drop(c)` and direct `remove_dir_all`. Merge queue success did not qualify that teardown or a release.

The scope probe is written at fake app-server startup, before its request completes. `manager::base` creates a separate runtime process group; dropping the service waits only for that service, so the runtime can still write `codex.log` or native session files. Native setup registers no projects, so it starts no board-observer TaskQ reads. The fake HTTP listener writes only in-memory state. No real model, token or board is needed.

The first repair passed exact-source CI on `aeee8156` and its native check passed merge-group CI `41297579153` on `cfd5aa30`. That merge group nevertheless failed: `a40_admission_startup_onboarding` hit `DirectoryNotEmpty` at `automatic.rs:185`. Admission and readiness both bypassed shared process-group `spawn` and cleanup. Their registered fake boards start observer reads in separate groups (`src/taskq.rs`), and startup onboarding also starts separate command groups (`src/onboarding.rs`). Killing/reaping the service alone does not end those writers. SQLite-only current-question/final-delivery callers have no external writers.

### Repair and evidence

The native check records its harmless fake runtime PID, waits for completed request delivery and process disappearance, then uses existing `spawn`/`stop` cleanup and asserts the exact path absent. Its waits share the original ten-second native-check deadline.

Admission and readiness now also use shared `spawn`/`stop`. Shared cleanup inspects process arguments for the exact absolute fixture `fake-taskq` executable and waits for its disappearance before removal. Service reaping prevents new observer dispatch; the fake TaskQ has no writer children. Inspection failure or an over-budget writer remains a failure. Writer waiting and removal share the original fifteen-second cleanup deadline. No global signals, blind sleeps, extra budgets or production lifecycle changes are added.

The persistent `fixture_cleanup_waits_for_detached_taskq` check owns a detached synthetic TaskQ writer gated by stdin. Against the original helper it failed with `cleanup returned while a detached writer was alive`, and the writer lost its final-write directory. Against the repaired helper it passes: cleanup waits for release and process exit, the last write succeeds, and the exact path is absent. This safely reproduces the ownership defect at the component boundary; it does not claim deterministic reproduction of the original native scheduling race.

Focused command `cargo test --locked --test telegram a40_ -- --nocapture` passed nine checks with the real fourteen-case suite ignored. Native scope equality, `env_clear`, no-token/no-board preflight and all fourteen live-case assertions remain intact. No ordinary service, credentials, grants, model or capacity changed. Candidate canonical checks passed: `scripts/check-contract.sh`, `cargo test --locked` (213 unit, 70 Telegram and 11 update checks; 11 live checks ignored), and `cargo run --locked -- selftest`. Independent read-only review found no blocking findings. The new regression failed against the original cleanup and passed after restoration of the candidate helper.
