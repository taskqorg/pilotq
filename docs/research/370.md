# Fresh release refs and multi-project status (#370)

## Question

PilotQ must observe current remote main/LIVE identities and answer a status request
for several authorized boards without asking for one destination.

## Findings

The binding requirements are [task #370](https://github.com/taskqorg/pilotq/issues/370)
and [PilotQ §5](../../pilotq.md#5-taskq-tools-and-project-administration).

- §5/R4: resolve each named board within current grants; an unbound board list cannot
  be narrowed by model arguments or historical project mentions.
- §5/R8: read configured main/LIVE refs from `origin`, including configurations using
  `refs/remotes/origin/...`. Pin the advertised SHA and fetch its objects for ancestry.
  A missing ref, failed remote read/fetch or exhausted deadline returns a named
  freshness failure, without falling back to local refs. Git diagnostics use the
  existing private executor (R16).
- §5: confirmation re-reads remote LIVE and refuses a changed preview before any
  release command. Main advancing never retargets its saved SHA.
- R13/§9/R19: these are shared tool-boundary Linux checks, not live Telegram,
  release, installation or production qualification.

### Failure before and pass after

At baseline `0be207e4a983a9f33a0fd21eb798d24054d2c368`, the two new regressions
failed: `remote_refs_370` returned the stale local LIVE SHA; `status_scope_370`
returned `Which project: cyprusbz, pilotq? Nothing was done.` Both passed after
the implementation fix with `cargo test --locked --bin pilotq 370` under Linux.

The final `release::tests` filter passed all 15 cases. Its remote fixture verifies
stale/missing local branches, stale tracking refs, remote-only commit objects,
status ancestry, missing/unreachable remote failures, preview freshness refusal,
and refusal of changed LIVE without dispatch. Existing grant, pinned target,
single-use confirmation, prerequisite, recovery and pipeline protections remain.
The old generic Git-error assertion now requires the A1 freshness reason; it still
requires unknown LIVE inclusion while retaining independent pipeline evidence.

The status regression covers multi-project ordinary/release reads, a subsequent
cs-only read, and an unbound release read with a guessed model project. It checks
the exact boards read, one snapshot per board and zero `project_question` events.
This required changing the caller in `src/taskq.rs` as well as `src/release.rs`.

### Unnamed follow-up rework

Review at `08657f21d03c2daf4560d214121b5d40beb3d171` found that the subsequent
unnamed request still aggregated every board. Extending `status_scope_370` with
“same board again, please” reproduced three reads instead of one. The regression
failed before the dispatch fix and passed afterward under Linux.

The manager now supplies the existing `source_request` convention for a semantic
one-board follow-up (§2, R13). The boundary requires an earlier answered input
from the same caller, route and generation with exactly one distinct successful
board-status read receipt. It resolves that receipt against current registrations
and grants before reading; a contradictory project argument is refused. The manager
omits the source for a new or all-board list. Explicit all-board intent in the current
own text also overrides a supplied source at dispatch, retaining §5 aggregation
even when the model supplies the previously read project. This adds no required human reply syntax,
time window, persistent selection or mutation authority.

The retained regression covers chained English/Russian unnamed follow-ups,
ordinary/release reads, and broad lists with both matching and guessed project
arguments. Missing, malformed, multi-board, foreign-caller, foreign-route and
old-generation sources, contradictory targets and revoked access are refused
without a board read. Existing ambiguous-history target checks remain unchanged.
The focused TaskQ filter passed all 21 cases; release checks retain A1/A2.

### All-board intent rework

Review at `d09bebf0e0ec7698a64eb9a95b8900ff05827a37` found the converse scope
failure: a new all-board request with a valid previous one-board source still read
one board. Extending the retained `status_scope_370` regression reproduced
`list all boards` reading one board instead of three before the fix. The same
Linux filtered check passed afterward.

Dispatch now recognizes explicit English/Russian all-board or all-project scope
in the current caller's own prose before applying a source. It then uses the
existing status resolution, including route bindings and current grants; no
new authority or persistent selection is added. The regression covers both
languages with a valid earlier one-board source, misleading project arguments,
ordinary/release status, and registered/accessible project wording. A same-board
request for all tasks with a quoted all-board phrase still reads one board.
Existing provenance, contradictory-target and revocation refusals remain covered.

The first Linux test invocation encountered CRLF in an embedded document before
reaching either defect. Canonical LF preparation resolved that checkout issue;
the subsequent failures above, not that setup error, establish reproduction.

Candidate gate results and the immutable candidate SHA are recorded in the TaskQ
result and PR. Live replay of #198 requests 505/507 and merge-result CI acceptance
remain separate from the local regression evidence. No deployment is performed.

## Options

- Resolve the remote identity and fetch its objects: current state and usable
  ancestry, at the cost of bounded remote reads. Implemented.
- Retain local-ref reads: no remote latency, but missing/stale branches violate A1.
  Rejected by the task's existing acceptance, without a new product decision.

## Verdict

Confirmed: stale local resolution, single-project dispatch, premature unnamed
status aggregation and source-based narrowing of explicit all-board intent caused
the reproduced failures. The regressions pass after
the scoped fixes. The first canonical Linux gate
passed on `cfad501ec77193a6a087d389d6b03860b4fcc097`: contract lint, 334 tests
passed/15 explicitly ignored, and offline selftest. The subsequent report-format
correction changed documentation only. That gate predates the follow-up rework;
the new candidate's gate and exact SHA are recorded separately in TaskQ and the PR.

## Recommendation

Accept the implementation subject to the existing merge-result CI and TaskQ review
gate. Keep live Telegram replay and deployment qualification separate (§9/R19).
