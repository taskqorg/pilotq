# Russian, English and Hebrew speech (#344)

The owner’s [task #344](https://github.com/taskqorg/pilotq/issues/344) requires: “Owner requires real recognition of Russian, English and Hebrew (Israeli means Hebrew) in existing audio intake. Remove Russian-only limitation; preserve native agent models and host capacity.” Sections 1 and 3 own the language and engine decisions. This report separates source verification from installed-host and Telegram qualification (R19, §9).

## Diagnosis and inventory

The previous implementation unconditionally passed GigaAM’s transducer encoder/decoder/joiner arguments. GigaAM v3 is a Russian model, not a multilingual recognizer. The manager’s conversation policy also explicitly refused non-Russian transcripts; the voice marker and video speech note described every transcript as Russian. Changing that instruction alone cannot add recognition.

All admitted voice notes, audio files and audio documents call `voice::transcribe`; video speech calls the same function after frame extraction. Telegram classifies audio MIME types and `.ogg`, `.oga`, `.opus`, `.mp3`, `.m4a`, `.wav`, `.flac` filenames at ingress. CLI and Telegram share configuration, grants, journal and request audit (R13). Saved transcripts are reused; this task does not rewrite stored recordings or historical transcripts.

The approved baseline was ffmpeg plus static sherpa-onnx-offline 2.0.1 and GigaAM v3 RNNT-punct int8. No recognizer was available on this worker’s PATH. Experiments used verified upstream assets in temporary storage, not installed services, credentials or model APIs. Native agent models, roles, slots and capacity configuration were not changed.

## Real-audio evidence and rejected options

Distinct human FLEURS recordings and references are retained in [the fixture manifest](../../tests/fixtures/speech/README.md), with CC BY 4.0 attribution. They are read speech, not synthesized transcripts or a language-detection mock.

The new `multilingual_344` reproduction failed against the original implementation with `voice recognizer failed`: the GigaAM arguments cannot load Whisper. The first Sherpa Whisper implementation recognized Russian and English but failed reading Hebrew output as UTF-8: byte-BPE token metadata splits UTF-8 characters even when the joined transcript is valid.

Sherpa Whisper small int8, turbo int8 and turbo with an unquantized decoder all recognized the Hebrew language but produced incomplete, incorrect wording. No run is counted as Hebrew acceptance. The retained Hebrew key-word check remained red. Turbo int8 on the WAV fixtures took 11.51/14.44/16.57 seconds (ru/en/he); cumulative child peak RSS reached 1,639,952 KiB on an Intel Xeon E5-2620 v3 CPU with four recognizer threads. These figures include process/model loading; they are not host capacity qualification.

Sherpa 2.0.1’s [decoder](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-whisper-greedy-search-decoder.cc) caps output at six tokens per second and half the text context. Hebrew byte tokens exhaust this cap before the recording finishes. Increasing tail padding did not remove the cap. Padding the recording to 25 seconds produced repeated nonsense rather than reliable speech. These approaches are rejected, not a reason to weaken the fixture assertions.

The Sherpa executable archive SHA-256 matched GitHub release metadata (`ea25c18660047a8ec8aa0cda291ccf806ae9c18a9b3b76372399cc4a7f4d7663`). Turbo encoder/decoder hashes matched the upstream exporter’s Hugging Face LFS metadata. Sherpa uses Apache-2.0; Whisper model weights use MIT. Neither license nor successful exit proves recognition quality.

## Selected engine and verified assets

Use CPU-only whisper.cpp 1.8.2 and multilingual Whisper small Q5_1. It produces the full Hebrew sentence without Sherpa’s six-token-per-second cutoff. Its short read-speech output still has technical-word and spelling errors; it is not verbatim accuracy or noisy-speech qualification. The permanent Hebrew check requires meaningful original-language text across the recording, including its final phrase, rather than accepting only a language label or requiring error-free morphology. The original GigaAM path cannot pass this check, and Sherpa’s truncated output cannot pass the final-phrase check.

- Engine source: [whisper.cpp v1.8.2](https://github.com/ggml-org/whisper.cpp/tree/4979e04f5dcaccb36057e059bbaed8a2f5288315), commit `4979e04f5dcaccb36057e059bbaed8a2f5288315`, MIT license. The local CPU build used `BUILD_SHARED_LIBS=OFF`, `GGML_NATIVE=OFF`, four build jobs and no source changes. Native agent models were untouched.
- Local tested executable SHA-256: `30ab87ffca69ba2e03f6c9c110c158cc5d7e4099eaa0179793559215b99aed70`. This identifies this compiler/build, not all owner-provisioned builds. Doctor verifies each installed binary against its own owner-provisioned version/hash receipt (§9).
- Model: [ggerganov/whisper.cpp, ggml-small-q5_1.bin](https://huggingface.co/ggerganov/whisper.cpp/blob/main/ggml-small-q5_1.bin), converted/quantized OpenAI Whisper small, 190,085,487 bytes. SHA-256 `ae85e4a935d7a567bd102fe55afc16bb595bdb618e11b2fc7591bc08120411bb` matches the upstream repository’s LFS object identity. Model weights and conversion project use MIT; retain their license notices when provisioning. Do not substitute an `.en` model.
- ffmpeg used for local real-media checks: 8.0.1. Its managed-host minimum remains 6.1.0. whisper.cpp’s new minimum is 1.8.2; the existing recognizer version/hash receipt mechanism is reused.

With four CPU threads, the production decoder/recognizer path took 22.39/22.02/24.13 seconds for ru/en/he Ogg/Opus (8.28/11.46/12.12 seconds of speech). A separate full Hebrew WAV run measured 352,800 KiB peak child RSS and 23.84 seconds, including process/model loading. The prior GigaAM benchmark reported 378 MiB on a different CPU; these observations do not establish throughput equivalence or aggregate host capacity. No slots, grants, thread configuration or host policy were changed.

The initial real ten-second readiness check timed out during language detection on digital silence. Verified zero-PCM segments now use a one-second encoder context and a fixed probe language, still run the real model and require a new valid JSON result; no generated words from digital silence are delivered. Actual speech always uses automatic language detection and full model context. The original ten-second probe budget and recording/turn deadlines remain unchanged.

The shared function retains the 20 MiB ingress cap, five-minute decoded cap, at most 25-second source segments, original deadline, subprocess fencing, private temporary directory and cleanup. Every segment has a unique JSON output path, so a successful exit without a fresh result cannot reuse the prior segment. Malformed JSON, invalid UTF-8, missing output and damaged transcript text fail explicitly. The manager keeps captions, source boundaries, original-language Hebrew, chat-language replies and the sender’s existing authority (R13, R16, R17, §12). No native sessions, journal schema or stored historical transcripts are rewritten.

Reproduce real speech checks after provisioning the verified assets into a separate test directory. Set `PILOTQ_TEST_RECOGNIZER` to that verified CPU executable and `PILOTQ_TEST_VOICE_MODEL` to the directory containing the verified model, then run:

```sh
cargo test --locked --bin pilotq multilingual_344 -- --ignored --nocapture
cargo test --locked --bin pilotq multilingual_containers_344 -- --ignored --nocapture
```

The first check uses three real human Ogg/Opus fixtures. The second checks the real bounded silence/model probe, corrupt input, MP3 speech and MP4 frames/speech. The fake-Bot-API test `telegram_voice_becomes_sender_text` additionally carries a true Ogg/Opus document through admission, transcript persistence and delivery; fakes establish plumbing only. Existing long-audio, five-minute, 20 MiB, ignored-sender, timeout, redaction and cleanup guards remain in place. Ordinary offline CI does not download speech assets; it runs the protocol and failure checks, while these explicit real-engine checks require the verified external assets.

## Qualification boundary

Workers do not install or restart (§9). Before any installed model changes, the PM must review the final recognizer/model origin, hashes, license, measured resources and rollback instructions. Retain the current protected configuration, prior release, old model directory, existing data and active management work.

The PM must run final-source A40 management qualification and cleanup on a unique reserved `pilotq-e2e-*` host, then follow the merge-queue release/install path. Real Chrome Telegram acceptance must send distinct Russian, English and Hebrew voice notes, audio uploads, true Ogg/Opus documents and video speech; inspect meaningful original-language transcripts, readable Hebrew, chat-language answers and durable audit. Also check silence, corrupt input, five-minute/20 MiB limits, restart reuse, fencing and cleanup. CI or a local recognizer exit does not prove any live case.
