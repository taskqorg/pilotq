# Russian, English and Hebrew speech (#344)

The owner’s [task #344](https://github.com/taskqorg/pilotq/issues/344) requires: “Owner requires real recognition of Russian, English and Hebrew (Israeli means Hebrew) in existing audio intake. Remove Russian-only limitation; preserve native agent models and host capacity.” Sections 1 and 3 own the language and engine decisions. This report separates source verification from installed-host and Telegram qualification (R19, §9).

## Question

Which existing-access offline recognizer can deliver meaningful original-language Russian, English and Hebrew across the shared media intake while preserving safe 0.39 update and rollback?

## Findings

### Diagnosis and inventory

The previous implementation unconditionally passed GigaAM’s transducer encoder/decoder/joiner arguments. GigaAM v3 is a Russian model, not a multilingual recognizer. The manager’s conversation policy also explicitly refused non-Russian transcripts; the voice marker and video speech note described every transcript as Russian. Changing that instruction alone cannot add recognition.

All admitted voice notes, audio files and audio documents call `voice::transcribe`; video speech calls the same function after frame extraction. Telegram classifies audio MIME types and `.ogg`, `.oga`, `.opus`, `.mp3`, `.m4a`, `.wav`, `.flac` filenames at ingress. CLI and Telegram share configuration, grants, journal and request audit (R13). Saved transcripts are reused; this task does not rewrite stored recordings or historical transcripts.

The approved baseline was ffmpeg plus static sherpa-onnx-offline 2.0.1 and GigaAM v3 RNNT-punct int8. No recognizer was available on this worker’s PATH. Experiments used verified upstream assets in temporary storage, not installed services, credentials or model APIs. Native agent models, roles, slots and capacity configuration were not changed.

## Options

- Retain GigaAM: preserves existing assets, but cannot satisfy English or Hebrew. Rejected.
- Reuse Sherpa Whisper: shares the installed engine, but observed Hebrew truncation and metadata failures prevent acceptance. Rejected.
- Use whisper.cpp small Q5_1: produces meaningful complete ru/en/he text with bounded measured resources, but requires a separately verified engine and retains Hebrew technical-word errors. Selected.

### Real-audio evidence and rejected options

Distinct human FLEURS recordings and references are retained in [the fixture manifest](../../tests/fixtures/speech/README.md), with CC BY 4.0 attribution. They are read speech, not synthesized transcripts or a language-detection mock.

The new `multilingual_344` reproduction failed against the original implementation with `voice recognizer failed`: the GigaAM arguments cannot load Whisper. The first Sherpa Whisper implementation recognized Russian and English but failed reading Hebrew output as UTF-8: byte-BPE token metadata splits UTF-8 characters even when the joined transcript is valid.

Sherpa Whisper small int8, turbo int8 and turbo with an unquantized decoder all recognized the Hebrew language but produced incomplete, incorrect wording. No run is counted as Hebrew acceptance. The retained Hebrew key-word check remained red. Turbo int8 on the WAV fixtures took 11.51/14.44/16.57 seconds (ru/en/he); cumulative child peak RSS reached 1,639,952 KiB on an Intel Xeon E5-2620 v3 CPU with four recognizer threads. These figures include process/model loading; they are not host capacity qualification.

Sherpa 2.0.1’s [decoder](https://github.com/k2-fsa/sherpa-onnx/blob/v2.0.1/sherpa-onnx/csrc/offline-whisper-greedy-search-decoder.cc) caps output at six tokens per second and half the text context. Hebrew byte tokens exhaust this cap before the recording finishes. Increasing tail padding did not remove the cap. Padding the recording to 25 seconds produced repeated nonsense rather than reliable speech. These approaches are rejected, not a reason to weaken the fixture assertions.

The Sherpa executable archive SHA-256 matched GitHub release metadata (`ea25c18660047a8ec8aa0cda291ccf806ae9c18a9b3b76372399cc4a7f4d7663`). Turbo encoder/decoder hashes matched the upstream exporter’s Hugging Face LFS metadata. Sherpa uses Apache-2.0; Whisper model weights use MIT. Neither license nor successful exit proves recognition quality.

## Selected engine and verified assets

Its short read-speech output still has technical-word and spelling errors; it is not verbatim accuracy or noisy-speech qualification. The permanent Hebrew check requires meaningful original-language text across the recording, including its final phrase, rather than accepting only a language label or requiring error-free morphology. The original GigaAM path cannot pass this check, and Sherpa’s truncated output cannot pass the final-phrase check.

## Hebrew semantic regression: acceptance remains open

PM note 6560920323 reports a distinct private synthetic Hebrew clip whose reference says three blue books. The production small Q5_1 output says `יש לו שש ספרים כחולים` (six). This is a semantic failure under §1 and A4, not a passing language-detection result. No private audio is published, and neither its reference nor the human fixture assertions were weakened.

The same verified executable/model were probed with automatic language detection, four threads, CPU only, no transcript prompt and a 120-second subprocess deadline. These are isolated worker measurements, not qualification under the PM host's 150% CPU limit or aggregate capacity proof. Peak RSS is the child high-water mark; the beam-8/human measurements share a parent, so the human peak is only a cumulative upper observation.

| Probe | Seconds | Peak child KiB | Observed result |
|---|---:|---:|---|
| Q5_1, ordinary beam 5 / best-of 5 / temperature fallback enabled | 23.451 | 473,012 | Wrong: six blue books; no fallback triggered |
| Q5_1, beam 5 / best-of 5 / temperature 0.2 | 23.415 | 472,624 | Wrong: six blue books |
| Q5_1, beam 8 / best-of 5 / fallback enabled | 23.766 | 533,888 | Wrong: six blue books |
| Q5_1, human Hebrew, ordinary defaults after 16 kHz mono ffmpeg decode | 28.432 | ≤533,888 | Readable through `ולא מותנות חברתית`, but word errors remain |
| Unquantized small, ordinary defaults | 22.449 | 767,180 | Wrong: six blue books |

A beam-10 probe exited 10 because this executable supports at most eight decoders; it is not quality evidence. A direct Ogg CLI probe produced no transcription and is excluded: the production ffmpeg decoder is necessary for this build. The human measurement above uses its decoded PCM, not that empty result.

The unquantized experiment used the same multilingual small model family and MIT license, downloaded only into ignored worker test storage. Origin: [ggml-small.bin](https://huggingface.co/ggerganov/whisper.cpp/blob/main/ggml-small.bin); 487,601,967 bytes; SHA-256 `1be3a9b2063867b937e64e2ec7483364a79917e157fa98c5d94b5c1fffea987b`, verified against upstream Hugging Face LFS metadata before probing. It is an unsuccessful experiment, not a replacement asset or part of the approved Q5_1 handoff manifest.

These observations refute the proposed ordinary-decoding repair for this clip. No production setting was changed and there is no green semantic repair to report. A larger multilingual speech model is the next technical option, with potentially higher memory/latency requiring bounded measurement and PM review before installed changes (A2, §9, R19). Accepting the known count error or supplying expected words to the decoder is not proposed. The original Q5_1 files, installed configuration, native agent models, rights, slots and capacity remain unchanged.

Readability and an ending keyword do not make the mistranscribed words correct (A4, R19).

For the recording-budget stress check, an explicitly repeated human Hebrew PCM fixture supplies exactly 300 seconds. Repetition is budget stress data, not an additional natural-speech quality case. The harness mirrors production's twelve 25-second source segments, launches the same arguments above and uses one monotonic 600-second deadline for all segments, killing the process group at expiry. Fixture construction precedes that deadline; a failure even without ingress/decode overhead is sufficient to reject full-recording feasibility. The full-recording probe **failed the 600-second deadline**. Five of twelve segments completed (125 of 300 source seconds). Segment times were 69.797, 114.704, 113.487, 126.953 and 112.084 seconds. The sixth process was killed at total 600.082 seconds (exit -9); later segments were never started. Peak cumulative child RSS was 931,448 KiB. No probe was retried or dispatched after this time failure. These measurements are retained with the exact arguments and JSON/stderr in ignored `target/pm344-medium-probe`; this is a subprocess/segmentation experiment, not an installed PilotQ or Telegram acceptance run.

Medium is therefore not a feasible drop-in selection under the measured five-minute/600-second combination, even excluding ingress/decode overhead. The ten-second silence algorithm fits in isolation, but production asset selection/readiness still names small: no claim is made that an unmodified installed doctor accepts medium. Repetition changes decoder workload, so this result proves this stress case fails; it is not an estimate of all five-minute recordings. Do not infer a safe longer deadline by linear extrapolation.

The concrete tradeoff is to retain the existing recording/deadline limits and evaluate a faster multilingual alternative (such as large-v3-turbo), or explicitly revise the input/latency requirements before selecting medium. Medium requires roughly 910 MiB peak child RSS in this run and still has human Hebrew errors; spending more time alone does not establish acceptable quality. The recommended next step is another bounded offline candidate evaluation within unchanged limits, not a capacity increase or acceptance waiver. No production implementation or installed model selection follows from this experiment (A2/A4, §§1/3/9, R19).

This identifies an encoder cost to investigate, not measured savings or permission to hard-code a language. No engine source, binary or detection behavior was changed in this evaluation.

The full-recording turbo stress probe **failed the unchanged 600-second deadline**. The five-minute cap, references and engine arguments were not changed.

Turbo therefore improves this private count and this one human Hebrew observation, and fits the isolated silence/readiness algorithm, but is not a feasible drop-in solution for the measured full-recording budget. Its smaller decoder does not make the measured automatic-detection CPU path faster than medium on the short clips. No per-stage timings were collected with suppressed engine logs: the source-inspected duplicate encode is a possible investigation target, not a quantified optimization or passing repair. The remaining product tradeoff is preserving input/deadline requirements while investigating a more efficient offline path, versus explicitly revising recording length/latency requirements. No limit, rights, capacity or native agent model change is made here.
