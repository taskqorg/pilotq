# Saved-answer confirmation (#338)

## Question

Why did repeated current-question presses keep a queued placeholder after the answer had already been saved, and how can confirmation survive an expired Telegram popup without repeating TaskQ work?

Owner requirement and scope: [task #338](https://github.com/taskqorg/pilotq/issues/338). R5/R11 and §§4–5 require durable, observable completion separate from transport delivery; R13 retains the shared request, grant and audit boundary. §9 reserves live qualification and installation for the PM.

## Findings

### Actual039 diagnosis

The PM-staged private receipts were inspected read-only in ignored `target`. Requests 403 and 404 came from two Chrome presses approximately ten seconds apart on the same current question, revision 37970. TaskQ recorded one accepted answer, 37981, and one mutation effect owned by request 403. Request 404 stored the existing answer and actor without a second effect or continuation. Its popup delivery 2616 failed with `Bot API rejected request`; queue notice 2615 had already been delivered and remained visible. The observed failure was confirmation delivery and queue finalization, not a duplicate board answer. Private route, person and callback identifiers are excluded from this report and public fixtures.

The callback answer path previously checked TaskQ before reading its saved local receipt. Terminal button replies were sent only as callback popups, whose short validity can expire while the original answer or queue is delayed. The delivery scan superseded unsent queue notices but never finalized delivered ones.

### Failure before and pass after

`cargo test --locked --bin pilotq saved_answer_338 -- --nocapture` failed against the implementation without the fix: `saved receipt must bypass worker at admission`, actual `queued`, expected `answered`. The same regression check passes after the fix. An initial `--lib` selection ran zero relevant tests and is not evidence; the existing pinned specq submodule required initialization before binary tests could compile.

The regression cases reuse the invented schema-13 question fixture and protect completed receipts, presses while the original write is pending, delivered queue notices, expired popups, restart, transient delivery retry, explicit errors, foreign routes, foreign source requests, changed revisions, registration changes and revoked decision grants. Delayed registration/access changes block confirmations and saved popups. Already delivered historical popups without a stranded queue do not replay as new chat messages.

The existing `u82_ask_buttons_and_labeled_links` fake-service chain now holds the original answer write until a rapid second press is admitted, then releases it and sends a completed-receipt press whose popup is rejected as expired. It verifies durable confirmation at the original topic and exactly one TaskQ answer dispatch. Original question rendering, option identity, actor, task links and reaction protections remain.

### Implementation and rule application

The journal owns a bounded local receipt scan at admission and delivery. It joins the exact delivered question, accepted-answer receipt, original request route, task binding and current registered board/root, and checks the presser's current decision grants. A newer question excludes the fast path. Pending writes remain pending until an accepted receipt exists; requests with their own effects remain with existing operation reconciliation. A worker holding an earlier answer-list snapshot rechecks the local completion before any board process. The original TaskQ operation/revision, stale and foreign write guards remain authoritative (§5).

A terminal callback answer commits one durable route-local confirmation. The ordered outbox edits that request's delivered queue notice, or sends the confirmation if no notice was delivered. Its existing rich/HTML/plain fallback and retry receipts survive restart. Failed historical popups and terminal requests with delivered queue notices can recover from exact original-question provenance. Delayed delivery rechecks registration and current grants. No recovery calls TaskQ, changes images, invents an actor or authorizes continuation (§4, R5/R11). Admission and terminal audit records retain the request identity and CoreQ trace (R13/R17).

The root contract and presentation owner now state the saved-receipt and durable-confirmation behavior; the conversation detail names its guards. No schema, dependency, access, runtime, model or capacity change is introduced.

## Options

- Use exact local receipts and the existing ordered outbox. Plus: prompt confirmation without another board call and durable queue finalization. Minus: one bounded local reconciliation scan. Selected.
- Keep popup-only delivery. Plus: no chat confirmation. Minus: popup expiry can permanently strand the queue notice and fails the goal.

## Verdict

The local journal and fake-service checks establish saved-answer confirmation without another TaskQ dispatch, including retry and recovery. PM-staged receipts establish the original live failure; they do not prove the changed candidate in Chrome.

## Recommendation

Review the 0.2.40 candidate, which already includes #331/#332/#334 through main, and require green merge-result CI. Then the PM runs one final-source A40 with independent cleanup, the ordinary release/install path and the actual Chrome repeat retest (§9, R19). The worker makes no live journal edits, Telegram calls, service changes or releases.
