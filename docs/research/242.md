# Unbound board list (#242)

An unbound read-only list must return every accessible registered board without a project question
([§5](../../pilotq.md#5-taskq-tools-and-project-administration), R13, R17).
The [task](https://github.com/taskqorg/pilotq/issues/242) preserves the request and acceptance.

## Question

Why did audit #253 reject its board-list tool call, and how can an unbound route return all
authorized boards in one turn while preserving task and mutation target checks?

## Findings

### Failure evidence and cause

The PM supplied scrubbed evidence in task note 6545502124 from PilotQ 0.2.32. Audit #253 had no
project, input `сделай таскью-лист`, and one failed dynamic tool item
`exec-a64b8489-486e-4419-a997-fa1f30c27954`. The rollout identifies `project_status`, arguments
`{"project":"pilotq"}`, `success:false`, and this returned error:

```text
Which project: cyprusbz, pilotq, tight? Nothing was done.
```

The resulting reply asked which board to show. No board read is evidenced.

`taskq::dispatch_until` sends project status through `direct::target_context`. Its
`target_inner` evaluates `context_project` before processing the explicit argument.
`context_project` checks the person's current message, then earlier own messages in the generation;
multiple matches immediately record a project question and return that exact error. Thus historical
ambiguity can reject the call before argument validation or any status read. The rollout does not
include those earlier messages; their exact contents remain unknown. This is a tool-boundary refusal,
not evidence of a Codex protocol failure.

## Change and protection

The unbound board-list path resolves all currently accessible registrations from the boundary,
ignoring model guesses and historical project mentions. Each board uses the installed TaskQ CLI
and a complete matching snapshot, with its own audit read. A failed board remains explicitly
unavailable while successful lists survive. Bound routes, current own project references, individual
tasks, release queries and mutations retain their target checks. The model receives instructions to
return all boards in one reply without clarification.

`unbound_242_board_list` exercises the recorded tool arguments against three registered boards,
ambiguous own history, command counts, audit counts, partial failure and revoked grants. Existing
`project_status_context_read` retains single-project integrity and mismatch/incomplete protections.
Local adapter evidence does not prove live Codex compliance or Telegram presentation.

## Local verification

Before the implementation change, `CARGO_HOME=/tmp/pilotq-242-cargo cargo test --locked unbound_242`
failed at the recorded `project_status` call with `Which project: pilotq, tight? Nothing was done.`
With the final three-project fixture and only the new aggregate branch disabled, the original resolver
also fails with the exact rollout error: `Which project: cyprusbz, pilotq, tight? Nothing was done.`
Restoring the candidate makes the same filtered check pass. `cargo test --locked project_status` also passes.
The single-board fixture now explicitly binds its route because #242 deliberately replaces historical
selection for unbound broad status. Its integrity, incomplete snapshot, board mismatch, unknown task
list and revocation assertions remain intact. No existing guarding assertion was removed or weakened.

Candidate gates: `scripts/check-contract.sh` passes (300 lines; a headroom warning remains),
`cargo test --locked` passes (169 unit, 62 Telegram adapter and 10 update tests; 11 existing cases
ignored), and `cargo run --locked -- selftest` passes. These checks use the temporary Cargo home.
Merge-result CI and post-release A3 are not established by these local checks.

The default Cargo cache was read-only in this sandbox. A fresh temporary `CARGO_HOME` permits
local compilation without changing host configuration or credentials.

## Options

- Keep single-project resolution for every status call. This retains the old resolver but repeats
  the observed clarification and fails A1.
- Resolve unbound lists as an authorized set of boards. This satisfies A1 and preserves scoped
  task/mutation resolution; the model must still present the combined result correctly in live TEST.

## Verdict

Confirmed: the original resolver reproduces the rollout error, and the aggregate path passes the
local regression. Live presentation and post-release A3 remain unqualified.
