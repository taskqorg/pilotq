# PM pack and scoped notes (#221)

The worker stage implements owner-installed PM context for route loops under PilotQ R13, R16, R18 and §9.
The owner confirmed staged delivery in [task #221](https://github.com/taskqorg/pilotq/issues/221): code and checklist first,
then PM shadow qualification. The task remains incomplete until the PM supplies the A7 live work and A8 comparison.

## Question

Can the existing manager and journal load an owner-installed PM runbook and durable scoped notes without adding
another scheduler, memory service or grant path?

## Findings

The [root contract](../../pilotq.md#9-cli-releases-and-service-operations) quotes the owner decision and defines the
pack and note boundary before implementation. [The runbook](../pm-pack.md) covers installed TaskQ board reads,
`taskq profile watch`, asks, steer, held-task admission, close, release prerequisites and linked workers reports.
The protected CLI installs bounded UTF-8 text, binds an exact route with optional registered-project narrowing and
lists, edits or forgets notes. Bindings and notes use the existing schema-12 journal metadata; no migration is needed.

Every eligible manager turn, including native resumes and synthetic ticks, receives the current runbook and note index.
Note tools recheck the active fence, owner/shell authority, registration and current project grants. Each note carries
one fact and one why line. Writes and request-scoped receipts are atomic; changed retries refuse. Index and tool
visibility follow the binding. Project scope narrows one route and never shares its notes with another route or DM.
Unbind hides the notes, while restart and `/new` retain them. CLI operations use the same scope/storage checks and
record actor, grants, operation and outcome in the journal. Notes remain historical context rather than board authority.

Known protected key values and recognizable credential syntax are refused before PM persistence. Pack text is bounded
to 16 KiB, each note to a 1,000-byte fact and 500-byte why, with at most 64 notes per route. Current key-store scrubbing
also protects turn input and CLI readback. Arbitrary prose cannot be proven secret-free; reviewed, secret-free seeding
remains mandatory (R16). Pack text is guidance and grants no additional authority.

## Verification

`cargo test --locked pm_221 -- --nocapture` passes four checks: three journal/component checks and one real CLI/manager
adapter check with a fake Codex transport and fake Bot API. They protect binding and help in English/Russian, note tools,
repeat/changed-argument receipts, optional project grants, synthetic tick context, route/DM isolation, credential refusal,
restart, `/new`, CLI edit/forget and revocation. The adapter check confirms the current note index on resumed turns;
it does not prove real model interpretation or PM parity.

The adapter check initially expected `dynamicTools` in `thread/resume` and failed at its unwrap. Inspection confirmed
that the existing protocol sends schemas at thread creation and reuses them on resume. The corrected check inspects
that creation schema while still asserting fresh context on both turns; it passes without changing adapter behavior.

The approved replacement of the no-skills clause exposed the old `/skills` assertion:
`cargo test --locked u106_telegram_controls_and_models -- --nocapture` failed at
`sent_has(&st,"No skills are enabled")`. The updated assertion requires the new PM-pack explanation and unavailable
callable native skills; the existing control-backlog, no-model, model-selection, callback and restart protections remain.
The same affected check passes after this accepted behavior update. No other decided assertion was removed or weakened.

The default Cargo cache is sandbox read-only, so checks use `CARGO_HOME=/tmp/pilotq-221-cargo`; dependencies were
fetched into that temporary writable cache. The tracked specq submodule was initialized at its existing gitlink without
changing the pin. Candidate checks and exact source identity are recorded in the PR; merge-result CI remains required.

## Options

- Existing journal metadata and manager tools. Pro: preserves the shared admission, recovery and audit paths;
  con: packs are bounded text rather than an extensible skill system. Implemented (R12).
- A new skill or memory framework. Pro: more extension mechanisms; con: adds authority and synchronization surfaces
  outside this task's need. Not adopted.
