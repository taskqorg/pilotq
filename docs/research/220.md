# Route loops and board wakes (#220)

PilotQ implements owner-authorized route loops through the existing journal, manager and TaskQ CLI. The owner decision is quoted in [the contract](../../pilotq.md#2-conversation-admission-and-authorization) and [the loop protocol](../conversation-contract.md#route-loops-and-board-wakes); task [#220](https://github.com/taskqorg/pilotq/issues/220) owns acceptance A1–A8. This applies R1, R5, R10, R13, R17 and R18 without changing §9 installation or production qualification authority.

## Implementation and retained protection

One persisted loop per front/chat/topic stores author, prompt, fixed/dynamic mode, generation, next time, pending tick and scoped board bindings. Enqueue and timer advancement are atomic. Existing requests own runs, context, audit, telemetry and replies. Human claims take priority; ticks reserve human capacity and share route exclusion. Board/root collectors share persisted cursors, qualify complete snapshots and confirm disappearing issues through installed TaskQ issue readback. Collection errors retain unknown status and timer fallback.

The deterministic controls and model tools share the admission and grant path (R13). A running synthetic tick loses authority immediately on reset or shell revocation. Start/stop receipts prevent changed-argument replay; stopped or replaced ticks cannot recreate loops. Drain retains armed and queued work. Restart uses the existing interrupted-native-turn no-replay rule (§§4–5).

## Before and after evidence

With the original `Journal::fenced` implementation temporarily restored, `cargo test --locked loop_220_running_reset_and_revocation_fence -- --nocapture` failed with `/new must fence the previous loop generation immediately` (exit 101). Restoring the generation and current-shell checks makes it pass. The retained test protects both reset and shell revocation before further effects, without weakening existing assertions.

`cargo test --locked loop_220_cli_route_exclusion -- --nocapture` initially failed with `CLI must not run beside its active loop tick` (exit 101). The synchronous CLI boundary now refuses while its synthetic tick runs, with a retry/stop remedy. The same test passes and also proves that a tick queues behind an active human CLI request.

`cargo test --locked loop_220 -- --nocapture` passed all six checks. The remaining cases cover parser/authority bounds, CLI and Telegram, dynamic delay, restart, drain, coalescing, revocation, two boards plus a human third route, independent context/replies, shared observation cursors, event deduplication and confirmed closure. Existing protection remains intact. Cargo uses a temporary cache because the default cache is read-only in the sandbox.
