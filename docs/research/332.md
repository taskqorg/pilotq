R4 and §5 require one authorized destination. The request in [task #332](https://github.com/taskqorg/pilotq/issues/332) requires respecting an explicit Russian destination while naming the tested product, preserving ambiguity and access guards.

## Question

Why did an explicit Russian destination conflict with the tested product, and can the shared resolver honor it without weakening ambiguity or access guards?

## Findings

The ignored private fixture preserves the observed failure of issue_read, project_status and task_plan. Their shared owner is `direct::project_role` / `select_project`, not tool-specific dispatch: “Проверяем продукт NAME” was unclassified, and “проект назначения задачи — только TARGET” did not prove an explicit destination. Both registered names therefore competed.

Before the fix, `PILOTQ_PRIVATE_332=target/pm-332-private-explicit-target.json cargo test --locked explicit_target_reference_plan` failed with `Which project: csgo, pilotq? Nothing was done.` The exact request was first in a temporary local input list. After the fix, the same command passed, exercising both direct target boundaries, project_status and saved plans. The temporary private loader was removed. No private source wording, identities or attachments are retained in tracked fixtures. An initial build could not compile because the pinned specq submodule was absent; initialization repaired the checkout, and that build was not counted as product evidence.

The smallest fix adds the missing product-reference and explicit-destination constructions to the existing shared classifier. It does not let an explicit target override an unclassified competing name. A second actual destination remains a conflict even when the same name also appeared as a tested product. The integration detail clarifies these constructions under the existing §5 decision; no decided assertion was weakened.
