# Adoption and recovery qualification (#199)

## Question

Can the remaining adoption protections be qualified without approving proposed thresholds,
agentq enablement or production cutover? Source: [#199](https://github.com/taskqorg/pilotq/issues/199),
following [#191](191.md) and [#26](https://github.com/taskqorg/pilotq/issues/26).
The hypothesis is that an evidence-led plan can cover each listed clause while preserving
owner gates. The decision rule is one executable recipe, named prerequisite or explicit
owner decision per clause, with unknowns never reported healthy. Budget: one research
attempt and report; no deployment, model evaluation or paid service.

## Qualification recipes

These procedures are proposed acceptance recipes, not commands to run on an installed service.
Use an isolated temporary installation with invented people and a separate bot. Preserve exact
candidate SHA, environment, fixture seed, initial state, fault event, final state and scrubbed
receipts. Failure or unavailable setup stays unknown; never substitute a fake for live proof.

### S — Pressure, pruning and replay tombstones

After owner approval of thresholds and retention, implement the controller in a separate task.
Use a bounded test filesystem or quota, not the host disk. Populate raw text, audit metadata/text,
inactive sessions, reconciled receipts, diagnostics and attachments on both sides of every
age boundary, alongside active plans, unanswered questions, uncertain effects and pending outbox.
Count journal, WAL, sessions and temporary files together. At the proposed 80% of 2 GiB,
verify only eligible content is pruned and one durable pressure alert is retained. At the
hard limit verify new CLI/Telegram admission refuses, unresolved records survive, and the
Telegram cursor stays unchanged for unstored input. Free space and restart; verify recovery
admits new inputs without redoing accepted work. Simulate an outage beyond 24 hours and
require an explicit possible-gap notice, never an assertion of recovered group history.

Prune reconciled content, then redeliver an old update and operation ID before and after
restart/restore. Require the same request/receipt and zero additional external effects.
Tombstones must retain identifiers, target/revision binding and enough outcome to reject replay,
without retaining pruned message bodies. Decide their expiry against actual replay sources;
90-day receipt content retention alone cannot justify tombstone deletion. Inject a crash
between selection and deletion; require atomic pruning or restart-safe progress. Measure reclaimed
bytes and alert delivery; inability to alert under full disk needs an independent host channel.

### R — Snapshot and restoration

Use SQLite Online Backup API (for example Python standard-library `sqlite3.Connection.backup`)
to a new file in the isolated fixture; never copy only a live main database while WAL is active.
Arrange a committed pending input, pending delivery, uncertain effect, completed TaskQ operation,
revoked grant and tombstone before backup, with a concurrent writer during the backup.
Run `PRAGMA integrity_check` on the snapshot and retain its SHA256 and schema version.
A consistent snapshot may precede a concurrent commit; record the actual snapshot boundary.

Restore into a second isolated installation with polling, model calls and real effects disabled.
Verify integrity, grants/revocations, routes/profiles, cursor, IDs, task links, receipts,
unanswered questions and delivery destinations against the recorded boundary. Reconcile the
fixture and feed duplicates; require no repeated mutation and only pending delivery retries.
Test newer-schema refusal and compatible rollback against both copies. Corrupt/truncate a copy
and require refusal, preserving the original snapshot. Native sessions, protected configuration,
attachments and keys need a separately reviewed manifest and consistent recovery plan; do not
claim a database backup alone restores them. Never copy key values into evidence. Decide backup
frequency, destination/access, retention, RPO and RTO before operational adoption. A successful
backup is not restore proof; record restore results independently.

### N — Native account and workspace binding

First decide a nonsecret stable account identity source and canonical workspace binding.
Persist them with the session, validate before resume and after reauthentication, and define
an explicit operator correction path. Do not read tokens or auth-file contents into the model.
In a fake-runtime fixture change account, workspace, missing identity and authentication state
independently; require refusal or explicit recovery, no silent session discard or API fallback.
Repeat with same identity and compatible schema; require resume with preserved receipts.
Interrupt a native effect before its terminal receipt; require unfinished/unconfirmed reporting
without replay. Real subscription/account entitlement needs owner-approved provider evidence
and a PM-authorized test, separate from catalogue presence or successful login (R9, §11).

### C — Dynamic-tool originals and paired context evidence

Read the current agentq dynamic-tool adapter contract and qualify its actual PilotQ call/result
boundary before any on run. Retain immutable original bytes, tool-call/result IDs, errors,
evidence location, route/project/actor and recovery reference. Exercise matching and foreign
routes, revoked access, reset generation, unavailable/corrupt original and oversized context.
Require exact-byte recovery after authorization, refusal for foreign/revoked requests, explicit
limits or bounded relevant retrieval on failure, and no repeated tool effect. Native compaction
and tool compression must each have one owner; assert no result is compressed twice.

Run identical C01–C07 fixtures off/on with fixed candidate, model, effort, prompts and repetitions
from [acceptance P1](../acceptance.md). Include multiple compactions, corrected preferences,
prohibitions, pending questions, immutable plan revision, grants, receipts and restart.
Capture completion, constraint violations, exact-original recovery, provider input/output/cache
tokens when available, latency and manual interventions. Missing token data is unavailable,
never zero or inferred from bytes. Apply the existing P1 gate unchanged; unsuccessful or absent
paired evidence leaves agentq disabled and native compaction baseline in place. Model evaluation
is outside this attempt's budget; PM authorization and available adapter are prerequisites.

### M — Migration, permission readiness and transport gaps

Review a manifest with each person's stable ID, grants/revocations, ordinary-group isolation,
shared-topic authorship, project registration and explicitly approved memories. Inventory every
Hermes goal and scheduled job with resume/retire/migrate disposition. On an isolated bot exercise
DM/group/topic admission and denied permissions, privacy and missing forum support; login alone
must not mark readiness. Record the last committed old-consumer cursor and in-flight inputs;
prove the old poller stopped before the new poller starts. Simulate a gap beyond Telegram's
24-hour retention and require an uncertainty notice, not invented history. Roll back by draining
or preserving accepted inputs/outbox, stopping the new poller and restoring the old consumer;
TaskQ-admitted work remains authoritative and is not refiled. Production handoff requires the
separate §10 acceptance and owner deployment grant.

### O — Startup, crash loop and rollback

Reuse existing update/drain/schema tests, then on the reserved PM qualification host inject
invalid config, unwritable storage, a held poll lock, unreconciled effects and a newer schema.
Observe startup ordering and require no polling/claims or healthy readiness before all gates pass.
The observed reconcile-before-lock order needs explicit verification of concurrent-start safety;
do not silently treat it as lock-before-reconcile. Crash three starts and observe bounded
backoff/rollback and incident deduplication. Kill or block the process and observe the external
host monitor; Telegram delivery cannot be guaranteed while both are unavailable. Roll back a
compatible build and prove queued work/outbox continuity; incompatible schema must refuse.
Use only merged released artifacts with §9 owner/drain constraints, never this research branch.

## Options

1. **Qualify in stages on the native baseline.** Plus: preserves existing authority and
   isolates each missing proof. Minus: storage, identity and agentq gaps remain open until
   implementation and authorized qualification complete.
2. **Keep the current test service with explicit limitations.** Plus: no new implementation
   or evaluation cost. Minus: does not close restoration, pressure or identity protections;
   adoption cannot progress through their gates.
3. **Treat local tests as adoption approval.** Plus: fastest nominal adoption. Minus: lacks
   restore/paired/host evidence and violates R19; inadmissible without changing owner decisions.

## Verdict

**Confirmed for the planning hypothesis:** every requested inventory clause has retained wording,
evidence limits and a recipe or prerequisite. **Inconclusive for operational qualification:**
no restore drill, disk-pressure run, identity-switch test, paired agentq run or migration occurred.
The absence of these observations is the missing evidence, obtained through recipes S/R/N/C/M/O.
No implementation defect was fixed, so no behavioral before/after pass is claimed.

## Recommendation

Choose option 1. The PM can decide technical sequencing after review. Ask the owner for final
retention/capacity, backup loss/recovery budgets, permitted telemetry and shared-subscription
entitlement before affected adoption. Keep agentq off until the adapter and measured P1 pass;
keep production replacement unauthorized until §10 gates and a separate deployment grant.
This report changes no decided rule, threshold, runtime authority or installed state (R19).
