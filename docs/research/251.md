## Findings

The initial `cargo test --locked --bin pilotq onboarding_251 -- --nocapture`
failed three regressions: `empty registered root has no clone`, claim findings
had `owner_only: true`, and `GitHub key cannot qualify GitLab`. The same filter
passes after the fixes, including the additional manager instruction-loading
case. The clone case was then strengthened to exercise actual registration with
a local Git transport fixture and verify checkout content and the exact requested
URL. No real GitLab board, host credential or service was changed.

- **A1, §5:** registration clones the caller's validated repository link before
  writing TaskQ configuration. The local fixture proves checkout content, origin
  reuse, foreign-origin refusal, file preservation, cancellation and missing Git.
  An invented authentication failure reports its category and exit code while
  withholding raw stderr, including from host logs (R16). Cloning uses the host's
  existing noninteractive Git setup; it does not copy TaskQ credentials or start
  a login. Unknown Git failures report the observed process outcome and code;
  their raw diagnostic remains withheld.
- **A2, §5:** missing `create_claim_issue` and Codex grants remain readiness gaps,
  with PM remedies rather than owner-only labels. The manager instructions direct
  authorized owner/shell turns to complete these steps and recheck. Typed
  onboarding does not silently create issues or grant access. The existing
  grant-output assertion changes from Owner to PM under the approved answer;
  stale evidence, unknown service state, capacity-versus-grant separation and
  refusal protections remain. Instruction loading proves availability, not live
  model execution or PM completion (R13, R19).
- **A3, §5:** the fallback records and displays a skipped GitLab MR route probe
  because it has no qualified route evidence. An unknown route does not block
  readiness. This proves neither MR publication nor merge-result CI.
- **A4, §5/R16:** the named `pilotq-gitlab` issue-read key must cover owner CLI
  and DM routes. A GitHub key cannot substitute; a missing GitLab key appears once
  with its protected-CLI remedy. This implements the acceptance's explicit
  missing-key alternative, not automatic import of an on-host token. Metadata
  inspection changes neither grants nor last-use time. TaskQ owns dispatch
  credentials; their values never enter the model.

Affected filters `onboarding` and `project_244` passed. Initial build setup needed
a temporary writable Cargo home and initialization of the existing specq gitlink;
these were environment failures, not passing behavior evidence. Candidate checks
and source SHA are recorded in the TaskQ result. Merge-result CI remains the
publication gate. Reverting the change restores previous onboarding behavior;
it does not remove any cloned root or undo PM setup effects.
