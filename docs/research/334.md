# Pre-upgrade question-control recovery (#334)

Task [#334](https://github.com/taskqorg/pilotq/issues/334), “Retire pre-upgrade superseded question controls during recovery,” requires exact receipt-based retirement without inventing answers. This applies the source-card and original-route requirements in §2, durable presentation recovery in §4 and qualification boundaries in §9/R19.

## Question

Which existing owner can retire pre-upgrade unanswered controls after the newer question has already been answered and the task closed?

## Findings

### Diagnosis before implementation

The PM staged private installed-0.2.39 journal receipts and post-update Chrome observations in an ignored target file. They show a delivered old question with controls and no accepted-answer receipt, a later question and accepted answer in the same request/project/task/route, retained images and a closed task subscription. The browser observations belong to the PM; this worker inspected only the staged evidence and never read or changed the live journal, clicked cards, restarted services or installed a build. No private bodies or route identities are copied here.

`Journal::observe` creates retirement obligations only when observing a new question. It returns early for an unchanged observation and excludes closed subscriptions. Existing answer recovery therefore cannot repair this old unanswered card, and neither a fabricated answer nor a repeated TaskQ action is appropriate. The owning layer is journal/outbox presentation reconciliation, invoked at startup and by the existing periodic delivery scan (§§2, 4, 12).

### Failure before and pass after

The invented schema-13 fixture in `src/fixtures/question-334-schema13.sql` contains old/new question receipts, an accepted current answer, an image receipt and a closed subscription, with no retirement obligation. Before the fix, `cargo test --locked --bin pilotq question_334_preupgrade_recovery -- --nocapture` failed with `pre-upgrade superseded controls must retire after restart`. The same check passed after the implementation change.

The initial `--lib` selection executed zero relevant tests and is not defect evidence. The first binary build found an uninitialized specq submodule; initializing the existing pinned gitlink restored compilation without changing the pin. Neither invocation is reported as a passing regression check.

### Implementation and protection

The existing startup reconciler and delivery scan now queue at most 64 missing retirement obligations per scan. Recovery requires a delivered original with a positive message receipt and parsed question metadata, a later parsed question with a higher revision and outbox identity, and exact request/project/task/chat/topic matches. The saved task binding must match the current registered board/root and original request route; current chat and project access are required. Closed task subscriptions remain eligible because retirement is presentation, not execution.

Ambiguous original receipts and missing, malformed or foreign provenance fail closed. The recovery obligation pins the original message ID and retains its original text plus the existing localized supersession statement. The ordered outbox owns retries and rich/HTML/plain fallback. Pending originals become eligible only after acquiring their delivery receipt. Current question buttons, images and accepted-answer author/revision remain intact. No schema, dependency, model, capacity or access-policy changes are introduced.

An accepted answer suppresses a pending retirement, including after restart or during retries. Recovery obligations recheck route, registration and access before dispatch; unavailable authority blocks the obligation. Existing stale/repeated/foreign callback checks remain authoritative. Recovery writes no answer receipt and calls no TaskQ mutation.
