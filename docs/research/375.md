## Findings

The root contract states the flow before implementation (§5, A1). `server_inventory` uses the existing manager and the owner-configured local DashQ report. It adds no agent, collector, credential store or remote command. `servers` and `server:WORKSPACE/HOST` grants gate reads; project ownership alone grants no server access. Telegram `/start server-DIGEST` selects a readable row without granting access. Advice and forecasts cite the returned observations; missing values remain unknown. Proposed changes reuse `task_plan` and its immutable confirmation, project, admission and receipt boundaries (R10, R13, R16, §§2, 4, 5).

The rework preserves the prior implementation and merges current main without rewriting the already published branch. Review regressions ran on Linux through WSL, using the same tracked sources with LF checkout bytes. The first setup attempts exposed a missing `specq` checkout and Windows CRLF instruction parsing; initializing the pinned submodule and normalizing checkout line endings removed those environment obstacles without changing their committed content.

Removing these last two guards reproduced the old-draft and preparation-race failures (11 passed, 2 failed); restoring them passed all 13 cases.

After the fixes, `cargo test --locked --bin pilotq servers:: -- --nocapture` passed all 13 cases. Existing refusal, unknown-field, data-age, ordering, exact-process-argument and digest-vector checks remain. `cargo test --locked start_375` also passed the actual admission/control check. The source has no server mutation operation. For owner/shell principals, the no-server-command rule remains a manager instruction under §5; these tests do not establish live model compliance.
