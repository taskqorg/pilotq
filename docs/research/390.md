# Long Codex manager thread recovery (#390)

PilotQ resumes the saved Codex thread without asking the adapter to return its history.
This implements [task #390](https://github.com/taskqorg/pilotq/issues/390), preserving
native context and effect receipts under R5 and §§4–6. Live qualification belongs to
the PM under §9 and R19.

## Question

How can PilotQ resume a long native Codex thread without loading its history,
changing its context or repeating effects, and retain reliable candidate checks?

## Findings

- Read [AgentQ report 253 at the requested result](https://github.com/taskqorg/agentq/blob/0ba341d875ac82f24049340a68a188b8a7f49580/docs/research/253.md)
  and its current TaskQ review. The accepted follow-up result is
  `9ac8a79d9d502af61f6c19d910121b23337255c0`: the mechanism is reproduced, but retained
  metadata cannot distinguish size from EOF for live requests 714/716.
- PilotQ sends `excludeTurns: true` only on resume. The model catalogue, new-thread
  tools, AgentQ pin, record bound, grants and receipts retain their existing behavior.
  Merged #385/#387 remain in the branch's main ancestry.
- [Long-thread acceptance](../acceptance.md#long-thread-resume-390) records the
  fixture's failure before the fix and pass afterward. It checks the same thread,
  one unchanged input, no new thread, no rebuild, and continued rejection of an
  oversized reply. Real Codex model-context evidence remains AgentQ's offline
  measurement; it does not qualify Linux native behavior or the live pilot.
- Handshake failures explain that input was not submitted, retain the conversation,
  and give the next action in English and Russian. Adapter diagnostics stay in
  protected operator logs; the person receives no raw native text (R11, R16, §8).

### Merge-queue fixture repair

Merge-group [run 42142804437](https://github.com/taskqorg/pilotq/actions/runs/42142804437)
at `fff70d09678acd5c50d7f315ff904f92b0077145` passed unit checks but failed
`concurrent_codex_starts_do_not_race` with `timed out: three answers`.

The fixture put three serialized half-second startups under a two-second
first-event watch. A bounded Linux probe increased only the invented startup delay
to one second. Before the repair, one request answered and two failed with
`Codex CLI sent no first event within 2 s`. With the same delay and a 30-second
fixture first-event budget, all three answer. The shipped fixture retains its
half-second delay and gets that budget plus a 45-second outer wait. CI's original
log did not retain individual request errors, so the probe establishes the timing
hazard rather than proving the exact cause of that CI run.

No assertion or production timeout changes. Concurrent-start failure, three
successful answers, raw-stderr exclusion and private-log diagnostics remain
protected. `f03_provider_faults_are_bounded` retains the two-second timeout and
uncertain-effect guards. Development checks and the canonical candidate gate run
on Linux through WSL; command outcomes and the exact candidate are recorded in
the TaskQ result.

### Handoff limits

No worker merge, release, installation, history edit, login/model/grant change,
uncertain-effect retry or waiting-task resume occurred. The PM must verify the
same native thread, journal continuity and real Telegram recovery on the existing
pds18 test pilot. The pre-existing generic resume-refusal rebuild and mid-turn
framing-error presentation remain outside this fix.

## Options

1. Exclude turns from the resume reply and give the serialization fixture its own
   budget. Pros: bounded replies and unchanged context, with concurrency protection
   independent of runner speed. Cons: real native recovery still needs PM checks.
2. Retry unchanged or raise the runtime record bound. Pros: less immediate editing.
   Cons: the fixture timing hazard remains and growing histories eventually exceed
   any larger bound; raising the bound also violates acceptance A2.

## Verdict

Confirmed for the offline resume mechanism and the fixture timing repair. The
exact cause of live requests 714/716 and real Linux native recovery remain
unproved; the PM must close those gaps on the existing test pilot.

## Recommendation

Accept the bounded caller fix and fixture repair after fresh merge-group CI; keep PM live qualification separate.
